# bench

Calliopi의 모델 벤치마크입니다. 같은 과제를 실행 조건(arm: 모델 × effort × 하네스 on/off)별로 반복해 돌리고, 결정적인 정답 검사(oracle)로 차원별 통과/실패를 매깁니다. 모델별 경향, 버전 간 회귀, 과제 종류별 비용 임계점을 근거로 남기는 것이 목적입니다. 근거 기준은 `docs/research/agent-self-improvement-evidence.md`에 있습니다.

```bash
npm run bench -- bench/specs/smoke.yaml               # faux 모델로 실행기·채점·리포트 확인 (비용 없음)
npm run bench -- bench/specs/s1-coarse.yaml --dry-run # 계획된 실행 목록과 spec 검사
npm run bench -- bench/specs/s1-coarse.yaml           # 실제 모델 호출: 비용이 듭니다
npm run bench -- bench/specs/s1-coarse.yaml --jobs 4  # 동시에 4개까지 (spec의 concurrency 대신)
npm run bench -- --report bench/.out/<spec>           # 기록된 실행으로 리포트
npm run bench:test                                    # 타입 검사와 단위 테스트
node bench/rescore.ts [기록.tgz|디렉터리] [--out 표.md] [--records 디렉터리]   # 기록을 지금의 채점으로 다시 매김 (모델 호출 없음)
```

temperature 같은 sampling 값은 실험 축이 아닙니다. 대상 모델은 thinking이나 추론 모델이라 provider가 받지 않거나 Pi가 보내지 않습니다. 조절하는 값은 effort이고, 무작위성은 반복과 중앙값으로 다룹니다.

## 구성
- `lib/catalog.ts`: Pi가 모르는 것만 둡니다. 계열, 계보(같은 제품군의 버전들)와 버전 순서, 가설 등급입니다. 가격, context, 지원 effort는 실행 시 설치된 Pi에서 읽습니다. 카탈로그의 모든 id가 Pi에 있는지 테스트가 확인합니다.
- `specs/*.yaml`: 실행 조건을 곱하지 않고 나열합니다. 실제 모델을 쓰는 spec은 `budgetUsd`가 있어야 하고, 이번 실행이 그만큼 쓰면 새 실행을 시작하지 않습니다. `concurrency`(기본 1, 최대 16)만큼 동시에 돌리고, `perProvider`로 provider마다 동시 실행 수를 따로 묶습니다(구독 한도와 rate limit은 provider 단위). 동시 실행 중에는 상한에 닿아도 이미 시작한 실행은 끝까지 가므로, 상한을 최대 동시 실행 수만큼 넘을 수 있습니다. 동시에 돌린 실행은 기록에 `concurrency`가 남고, 그 소요 시간은 순차 실행과 비교하지 않습니다. effort를 목록으로 주면 effort마다 조건 하나가 됩니다. 같은 조건을 반복하려면 `label`을 붙입니다(노이즈 대조). `harness: off`는 Calliopi 확장 없이 Pi만 돌립니다. `harnessRef: <git ref>`는 그 시점의 Calliopi를 worktree로 꺼내(`npm ci` 포함, 커밋마다 한 번) 씁니다. 프롬프트나 역할을 바꾸는 PR의 전후를 같은 시간대에 비교할 때 씁니다. 모델이 받지 않는 effort는 Pi가 몰래 다른 값으로 바꾸므로 spec 검사에서 거부합니다.
- `tasks/<class>/<name>/`: `task.yaml`(프롬프트, 버전, 변경 허용 범위, oracle)과 `fixture/`, 수정 과제는 모델이 보지 못하는 `hidden/`. 종류는 search, small-fix, multi-file, review(종류마다 기본 과제 3개와 `tier: hard` 과제 2개), 그리고 faux 전용 smoke입니다. hard 과제의 실행은 `<종류>-hard`로 따로 집계되어 기본 과제의 성공률·임계점과 섞이지 않습니다. 테스트가 과제마다 "아무것도 안 하면 실패, 기준 답이면 모든 차원 통과"를 확인합니다. 프롬프트·fixture·oracle·숨긴 테스트를 바꾸면 `version`을 올립니다. 리포트는 과제마다 기록된 가장 새 버전만 셉니다.
- `run.ts`, `lib/run.ts`: 실행마다 fixture를 저장소 밖 임시 디렉터리에 복사하고(git 초기화 포함) `pi -p --model <M> --thinking <effort>`를 돌립니다. 사용자 확장·스킬·AGENTS.md는 읽지 않습니다. 결과는 `bench/.out/<spec>/runs.jsonl`에 쌓이고, 실행별 답변·세션·남은 파일은 `runs/` 아래에 남습니다.
- `lib/report.ts`: 조건 × 과제 종류별 엄격 통과율과 반복 간 최악–최고, 차원별 통과율, 추가 지적 수, 실행당 비용·턴·토큰의 중앙값과 범위(캐시 적중이 실행마다 0~89%로 흔들려 한 번의 비용은 대표값이 못 됩니다), 캐시 적중, 도구 오류, 병렬 호출 비율, 범위 초과, 시간 초과. 종류별 임계점(엄격 통과로 최악 반복이 목표에 닿는 조건 중 중앙값 비용이 가장 낮은 것), effort 포화점, 계보 내 버전 비교를 냅니다.
- `rescore.ts`: 기록된 실행(`answer.txt`, `work/`)을 지금의 oracle로 다시 매기고, 기존 판정과의 비교표, 판정이 바뀐 실행, 기록과 어긋나는 검사를 냅니다. 채점을 바꾸면 기존 기록에 돌려 바뀌는 판정을 사람이 확인합니다. `bench/records/`에 기록 묶음과 그 결과가 있습니다.

## 채점

판정은 모델이 아니라 결정적 검사만으로 합니다. oracle의 검사마다 차원(`dimension`)이 있고, 차원마다 그 검사가 모두 통과해야 통과입니다. 차원을 적지 않은 검사는 `outcome`입니다.

| 차원 | 검사 | 재는 것 | 적용 과제 |
|---|---|---|---|
| `outcome` | `command`, `answer`, `file`, `unchanged` | 제공된 테스트 통과, 최종 답의 값, 파일 내용, 건드리면 안 되는 파일 | 전부 |
| `diagnosis` | `diagnosis` | 버그마다 근거 표현(정규식 묶음, 대소문자 무시) 중 하나가 답 전체에 있음 | review |
| `citation` | `citation` | 답의 마지막 줄(`line N`, `lines N, M`)이 버그마다 그 버그의 줄을 하나 이상 지목함. 버그가 없는 파일(`citation: []`)은 아무 줄도 지목하지 않아야 함 | review |
| `coverage` | `content`의 `required` | 답이 꼭 말해야 하는 항목(정규식 묶음)이 답에 모두 있음. 수정 과제는 무엇을 바꿨는지, 답이 숫자뿐인 search 과제는 그 근거 | search 일부, small-fix, multi-file |
| `scope` | `scope` 목록(검사 없이 자동) | 범위 밖 파일을 바꾸거나 만들지 않음. `scope: []`는 읽기 전용 과제 | 전부 |
| `hidden` | `hidden` | 실행 뒤 `hidden/`을 작업 디렉터리 사본에 덮어 돌린 숨긴 테스트 통과 | small-fix, multi-file |

- **엄격 통과**(기록의 `pass`)는 과제에 있는 모든 차원의 통과입니다. 성공률, 임계점, 포화점, 버전 비교는 엄격 통과로 셉니다. 가중 합산 점수는 없습니다.
- **추가 지적**(`extraFindings`, 정밀도)은 review 답의 마지막 줄이 지목한 줄 가운데 어느 버그의 줄도 아닌 것의 수입니다. 실패로 치지 않고 따로 셉니다. 진짜 버그를 다 찾고 버그 아닌 것을 덧붙인 답은 엄격 통과이면서 추가 지적이 1 이상입니다. 줄을 잘못 짚은 답은 `citation`이 실패하고, 잘못 짚은 줄도 추가 지적으로 세어집니다.
- **답의 분량**(`content`)은 실패로 치지 않는 수치입니다. 답을 블록(문단, 목록 항목, 표의 행)으로 나누고 블록마다 셋 중 하나로 셉니다. **필요**: 필수 항목(review는 진단 항목)이나 프롬프트가 요구한 마지막 줄이 든 블록. **허용**: `content.allowed`에 맞는 블록으로, 근거와 증거, 검증, 지킨 제약, review에서 버그가 아니라고 설명한 것입니다. **잉여**: 어느 쪽도 아닌 블록. 목록 항목은 그 목록을 여는 줄("나머지는 주석과 일치합니다:")의 분류를 따릅니다. 리포트는 답 길이(단어 수 중앙값)와 전체 단어의 필요/허용/잉여 비율을 냅니다. 부실한 답은 `coverage` 실패로, 과한 답은 잉여 비율과 길이로 보입니다.
- 진단과 인용은 따로 매깁니다. 원인을 맞게 짚고 줄을 하나 틀린 답은 `diagnosis` 통과, `citation` 실패입니다. 줄만 맞고 근거가 다른 답은 그 반대입니다.
- 숨긴 테스트는 과제 설명과 소스 주석에 적힌 동작만 다른 입력으로 확인합니다. 테스트가 과제마다 제공된 테스트의 입력만 특수 처리한 수정을 만들어, 그것이 `outcome`은 통과하고 `hidden`은 실패함을 확인합니다. 채점은 작업 디렉터리의 사본에서 하므로 남는 `work/`에는 숨긴 테스트가 없습니다.
- 차원이 생기기 전의 기록(`dimensions` 없음)은 `pass`를 `outcome`으로 읽습니다.

한계: 진단 정규식은 2026-11-27 기록의 review 답 174개를 보고 만들었습니다(그 답에서는 놓친 것이 없고, 다른 과제의 답에는 하나도 맞지 않습니다). 처음 보는 표현의 맞는 진단을 놓칠 수 있으므로, `diagnosis`만 실패한 실행은 답을 읽어 확인하고 맞는 표현이면 묶음에 더한 뒤 버전을 올립니다. 추가 지적은 마지막 줄에 적힌 줄만 세므로, 본문에만 쓴 과잉 지적은 잡지 못합니다. 답의 분량에서 허용 블록은 말할 가치가 있었는지를 따지지 않으므로, 전부 허용 범주인 답은 세 배 길어도 잉여가 0입니다. 그 차이는 단어 수로만 보입니다. 블록은 통째로 한 분류라서 필요한 문단 안의 군말도 보이지 않습니다. 필수·허용 정규식도 같은 기록의 답을 보고 만들었습니다.

## 어려운 과제 (`tier: hard`)

기본 과제 12개는 2026-11-27 기록에서 97%가 통과해 모델을 가르지 못했습니다. hard 과제 8개는 그 기록에서 실제로 보인 약점을 겨냥합니다. **모델을 돌려 보지 않고 만들었으므로 난이도는 아직 확인되지 않았습니다.** `specs/s3-hard.yaml`이 첫 확인입니다.

| 과제 | 겨냥하는 것 | 틀리기 쉬운 지점 |
|---|---|---|
| `search/unused-flags` | 빠짐없는 열거 | 플래그 16개 중 5개가 읽히지 않음. 별칭·구조 분해·동적 키·JSON을 거친 읽기는 읽기이고, 설정만 하는 것·주석·test/·이름만 같은 CLI 옵션은 아님 |
| `search/purge-routes` | 호출 경로 추적 | 다른 이름으로 가져온 호출, 작업 이름에 따라 갈리는 표, 이름만 같은 `store.purge` |
| `small-fix/event-order` | 증상과 원인이 다른 파일 | 원인은 `events.js`의 문자열 비교. `stock.js`에서 다시 정렬하면 범위·결과 실패, 두 자리까지만 맞추면 숨긴 테스트 실패 |
| `small-fix/task-queue` | 테스트보다 넓은 명세 | 제공 테스트는 reject만, 주석은 "throws or rejects". throw를 처리하지 않으면 숨긴 테스트 실패 |
| `multi-file/soft-delete` | 요구 사항 7개 중 일부만 테스트됨 | 제공 테스트가 닿지 않는 count, 통계, CSV 열, 404, `?archived=1` |
| `multi-file/cents` | 명세의 정확한 반올림 | 할인·세금 "금액"을 반올림해 빼고 더함. 결과를 반올림하면 0.5센트에서 1센트 차이 |
| `review/bounds` | 과잉 보고 | 버그가 없는 파일. `no bugs`가 정답이고, 지목한 줄은 모두 추가 지적 |
| `review/token-bucket` | 버그 3개와 버그처럼 보이는 것들 | 단위(ms×초당), `>`와 `>=`, 정수 토큰만 세는 대기 시간. 순회 중 Map 삭제 등은 버그 아님 |

확인할 때의 기준: 모든 조건이 매번 통과하는 과제는 가르는 것이 없으니 더 어렵게 하거나 뺍니다. 어떤 조건도 통과하지 못하는 과제는 모델보다 과제(모호한 프롬프트, 지나친 숨긴 테스트)를 먼저 의심해 답을 읽습니다. `review/token-bucket`의 진단 정규식은 모델 답을 본 적이 없으므로 첫 실행의 review 답은 모두 직접 읽습니다. `tasks: all`인 spec(`s1-coarse`)은 이제 hard 과제도 포함합니다.

모든 기록에 Pi 버전, 하네스 커밋(`-dirty` 포함), 과제 버전이 남습니다. 같은 모델의 반복 조건 사이 차이보다 작은 차이는 노이즈로 봅니다.
