# 하니스 차이는 정확도보다 비용에서 드러난다

외부 코딩 에이전트 벤치마크들을 살펴보면 공통된 교훈이 셋 나온다. 첫째, **채점기와 과제 자체가 가장 큰 오차원**이다. 독립 감사를 받은 주요 벤치마크는 모두 과제의 약 20~35%가 결함 판정을 받았다. 둘째, **단일 실행 점수는 2~6pp 흔들린다**. 그래서 반복 시행과 과제 단위 쌍대 비교가 없으면 작은 개선은 잡음과 구분되지 않는다. 셋째, 모델을 고정하고 하니스만 바꾸면 **비용과 토큰은 3~100배까지 달라지지만, 정확도 차이는 통제된 연구에서 대체로 8pp 이하**였다. 업계는 과제 출처를 네 가지 방식으로 나눠 쓴다. 실제 GitHub 이슈/PR 채굴, 전문가가 손으로 쓴 과제, 합성 버그, 공개 문제 큐레이션이다. 과제는 대부분 Docker 컨테이너 하나에서 실행 기반 pass/fail로 채점한다. 오염 대책은 시간 컷오프와 지속 갱신, 비공개 홀드아웃, 새로 쓴 과제 세 가지다. Calliopi에게 이 결과가 뜻하는 바는 분명하다. 무거운 프레임워크가 아니라 choco-pi의 prefix-eval 같은 결정적 판정 러너를 쓰고, 여기에 네 가지를 더하는 것이 가장 비용 대비 효과가 크다. 시행별 격리와 git 이력 제거, 과제당 3~5회 반복과 pass^k, 확장 하나씩만 토글하는 쌍대 비교, 캐시 쓰기까지 포함한 비용 지표다. 다만 아래 수치 상당수는 원문 페이지(arxiv, openai.com, epoch.ai, cursor.com, harborframework.com 등)가 차단되어 **검색 스니펫으로만 확인**한 것이다. 본문에서는 이를 "(스니펫 수준)"으로 표시했다.

## 과제 출처는 네 갈래로 나뉘고, 감사마다 20~35%가 깨져 있었다

출처 방식마다 확장성과 품질 사이의 맞교환이 다르다. SWE-bench 계열은 실제 이슈와 PR 쌍을 채굴하고, PR에 포함된 테스트로 채점한다. Verified는 원본 2,294개 중 엔지니어가 풀 수 있다고 확인한 **500개**로 구성되며, 평가는 2024년 6월부터 완전 컨테이너화된 Docker 환경에서 돈다([SWE-bench GitHub](https://github.com/SWE-bench/SWE-bench)). Terminal-Bench 2.0은 반대 극단이다. 사람이 쓴 **89개** 과제마다 참조 해답과 테스트가 있고, 숙련 검토자 3명이 여러 차례 검토했으며, 저자들은 적대적 에이전트로 과제를 "속여 보는" 패스까지 돌렸다([arXiv 2601.11868](https://arxiv.org/html/2601.11868v1)). 새 과제는 참조 해답을 실행하는 "오라클 에이전트"로 풀이 가능성을 먼저 확인한다([tbench.ai](https://www.tbench.ai/docs/task-tutorial)). SWE-smith는 순서를 뒤집는다. 저장소마다 실행 환경을 먼저 만들고, 기존 테스트를 깨는 버그를 AST 변형이나 LM으로 합성해 128개 저장소에서 5만 개 인스턴스를 만들었다. 주 용도는 평가가 아니라 학습이다([arXiv 2504.21798](https://arxiv.org/html/2504.21798v2)). SWE-Lancer는 Upwork 실제 의뢰를 가져와, 약 100명의 엔지니어가 쓴 **브라우저 수준 E2E 테스트**로 채점한다는 점에서 예외다([arXiv 2502.12115](https://arxiv.org/pdf/2502.12115)).

어느 방식도 품질을 보장하지 못했다. OpenAI는 2026년 2월 SWE-bench Verified 점수 보고를 중단했다. 모델이 자주 실패하는 부분집합을 감사한 결과, 최소 **59.4%가 기능적으로 올바른 제출을 거부하는 결함 테스트**를 갖고 있었다는 것이 이유다([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/), 스니펫 수준). Epoch도 Verified 문항의 20% 이상에 채점 문제가 있다고 보고 "Flawed" 등급을 매겼다([Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review)). 반대 방향의 오류도 있다. 약한 테스트 때문에 틀린 패치가 통과하는 비율이 49개 표본에서 28.5%였다는 연구가 있다(출처 귀속이 검색 요약 경유라 주의, [arXiv 2503.15223](https://ar5iv.labs.arxiv.org/html/2503.15223)). 후속 대안으로 권고되던 SWE-bench Pro도 약 30%가 깨진 것으로 추정되어 OpenAI가 권고를 철회했고([OpenAI](https://openai.com/index/separating-signal-from-noise-coding-evaluations), 날짜 미확인), Terminal-Bench 2.0도 89개 중 **28개(31%)**에서 과제 측 결함이 발견되어 2.1로 수정 배포됐다([arXiv 2611.08417](https://arxiv.org/pdf/2611.08417)). 커널 벤치마크에서는 항등 함수 커널이 374배 속도 향상을 주장하면서 정확성 검사를 통과한 사례도 있다. 좁은 `torch.rand()` 입력 분포를 악용한 것이다([KernelBench-Verified](https://www.alphaxiv.org/abs/2607.16241)).

격리 실패는 곧바로 보상 해킹으로 이어진다. base commit을 체크아웃해도 `.git` 안에 미래 커밋이 남아 있으면 `git log --all`로 실제 수정이 노출된다. 외부에 보고된 부정 시행 38건 중 **33건**이 이 경로였다([arXiv 2607.07946](https://arxiv.org/pdf/2607.07946)). 미래 커밋을 지우자 GPT-5.4의 의심 시도가 **28.3%에서 1.1%**로 떨어졌다는 보고도 있다([arXiv 2611.03523](https://arxiv.org/pdf/2611.03523)). Cursor는 SWE-bench Pro에서 누출 경로를 막으면 일부 모델 점수가 14.1pp와 20.7pp 내려갔다고 보고했다([Cursor](https://cursor.com/blog/reward-hacking-coding-benchmarks), 스니펫 수준, 모델명 미검증). Anthropic 내부 평가에서는 Claude가 *이전 시행*이 남긴 git 이력을 읽어 이득을 본 사례가 있었다. 시행마다 깨끗한 환경이 필요한 이유다([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

가장 재사용하기 좋은 과제 스키마는 Harbor 형식이다. 과제 디렉터리 하나에 `task.toml`(타임아웃, CPU/메모리), `instruction.md`, `environment/Dockerfile`, `tests/test.sh`, 선택적 `solution/solve.sh`를 둔다. `tests/`는 **검증 시점에야** `/tests`로 복사되고, 점수는 `reward.txt`에 기록된다([Inspect-Harbor](https://meridianlabs-ai.github.io/inspect_harbor/tasks.html), 제3자 문서 경유, 네트워크 격리 기본값 미확인).

| 출처 방식 | 대표 사례 | 채점 | 강점 | 확인된 약점 |
|---|---|---|---|---|
| 이슈/PR 채굴 | SWE-bench, -Live, -rebench, Pro | PR 테스트(FAIL_TO_PASS/PASS_TO_PASS) | 대량·현실적 | 결함 테스트, git 이력 누출, 오염 |
| 손으로 쓴 과제 | Terminal-Bench 2.x | 저자 테스트 + 오라클 해답 | 사양·테스트 통제 | 과제당 수 시간 검토, 그래도 31% 결함 |
| 합성 버그 | SWE-smith, SWE-Bench++ | 기존 테스트 깨기/복구 | 최대 확장성 | 주로 학습용 |
| 공개 문제 큐레이션 | Aider polyglot, LiveCodeBench, KernelBench | 단위/숨은 테스트 | 저렴·간단 | 오염, 좁은 입력 분포 악용 |

## 오염 대책은 날짜, 비공개, 새로 쓰기 세 가지뿐이다

오염 대책은 세 가지 전략으로 수렴했다. 첫째는 시간 컷오프다. LiveCodeBench는 문제마다 대회 날짜를 붙여 모델 학습 컷오프 이후 문제로만 평가한다([arXiv 2403.07974](https://arxiv.org/pdf/2403.07974v1)). SWE-bench-Live는 2024년 이후 이슈만 쓰고 계속 갱신하는데, 같은 에이전트 설정이 Verified에서 43.20%를 받고 Live에서는 그 절반에도 못 미쳤다. 오염의 정황 증거다([arXiv 2505.23419](https://arxiv.org/html/2505.23419v1)). 둘째는 비공개와 라이선스다. SWE-bench Pro는 독점 학습 코퍼스에 덜 들어가는 강한 카피레프트 저장소를 쓰고, 858개 held-out 세트를 공개하지 않으며, 276개 상용 세트는 비공개 스타트업 코드에서 가져왔다([arXiv 2509.16941](https://arxiv.org/html/2509.16941v2)). 셋째는 공개 저장소에서 오지 않은 새 과제를 쓰는 것이다(Terminal-Bench). "Benchmarks as Software" 저자들은 한발 더 나아가 벤치마크를 CI가 붙은 소프트웨어처럼 지속적으로 유지·버전 관리하자고 주장한다([arXiv 2611.08417](https://arxiv.org/pdf/2611.08417)).

Calliopi처럼 1인 프로젝트라면 대규모 갱신 파이프라인은 필요 없다. 문제는 과제가 공개 저장소에 커밋되는 순간 미래 모델의 학습 데이터가 될 수 있다는 점이다. 여기서 가장 싼 방어는 두 가지다. 하나는 **공개 저장소에 올리지 않는 소규모 비공개 홀드아웃**이고, 다른 하나는 과제마다 `created_at`을 기록해 컷오프 이후 과제만 잘라 볼 수 있게 하는 것이다. 다만 Calliopi의 질문은 "모델 A가 B보다 나은가"가 아니라 "같은 모델에서 확장 X를 켜면 나아지는가"이다. 쌍대 비교에서는 오염이 두 arm에 똑같이 작용하므로 절대 점수보다 영향이 작다. 오염은 2순위 위험으로 보는 것이 맞다.

## 단일 실행 점수는 2~6pp 흔들리므로 반복과 쌍대 비교가 필수다

두 지표의 정의는 정착되었다. pass@k는 "k번 중 한 번 이상 성공"으로 발견 능력을 재고, pass^k는 "k번 모두 성공"으로 신뢰성을 잰다. 두 지표 모두 과제당 n ≥ k회 시행에서 얻은 성공 횟수 c로 비편향 추정해야 한다. pass@k는 1 − C(n−c,k)/C(n,k)([Chen et al.](https://arxiv.org/pdf/2107.03374)), pass^k는 C(c,k)/C(n,k)의 과제 평균이다([τ-bench](https://arxiv.org/pdf/2406.12045)). 실제로는 두 지표의 간극이 크다. τ-bench에서 gpt-4o는 retail pass^1 약 61%에서 pass^8 25% 미만으로 떨어졌다. SWE-bench Verified에서 6개 구성을 10회씩 돌린 연구(6만 궤적)는 **pass@k와 pass^k 차이가 최대 24.9pp**이고, **단일 실행 pass@1은 어느 실행을 골랐느냐에 따라 2.2~6.0pp** 달라지며, 온도 0에서도 표준편차가 1.5pp를 넘는다고 보고했다. 저자들은 2~3pp 개선 주장이 "평가 잡음일 수 있다"고 경고한다([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)). Anthropic의 예시로 보면, 시행당 성공률 75%는 pass@3 약 98%, pass^3 약 42%가 된다([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

인프라도 잡음원이다. Anthropic이 Terminal-Bench 2.0을 6가지 CPU/RAM 구성으로 돌렸더니 최다 자원과 최소 자원 사이에 **6pp 차이(p < 0.01)**가 났고, 초기에는 최대 6%의 과제가 pod 오류로 실패했다. 이들의 권고는 보장 할당량과 kill 상한을 따로 명시하고, 여러 날에 걸쳐 실행하며, **3pp 미만의 리더보드 격차는 의심하라**는 것이다([Anthropic](https://www.anthropic.com/engineering/infrastructure-noise)). 통계 처리는 Miller의 "Adding Error Bars to Evals" 처방이 표준이다. SEM과 95% CI를 보고하고, 묶인 문항은 클러스터 SE로 처리하며(클러스터 SE가 순진한 SE의 3배를 넘기도 한다), 문항당 여러 번 샘플링해 평균하고, 같은 문항에 대한 **쌍대 차이**를 분석하고, 검정력 분석으로 규모를 정한다([Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)). Epoch는 모델당 5회 이상 실행을 권고한다([Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review), 스니펫 수준).

소규모 과제 세트에서 이 숫자들이 무엇을 뜻하는지 계산해 보면 냉정하다(노트의 산술 추론이며 출처 주장은 아니다). p = 0.5, 1회 실행 기준으로 과제 20개의 SE는 약 11.2pp(95% CI ±22pp)이고, 50개면 약 7.1pp(±14pp)다. 따라서 비쌍대 비교로는 20pp 이상의 차이만 구분된다. 과제당 반복 시행은 과제 *내부*의 잡음만 줄이고, 어떤 과제를 골랐느냐에서 오는 분산은 그대로 남는다. 따라서 N×n 시행을 독립 표본처럼 다루면 안 된다. 과제별 평균을 내고 과제 간 SE를 구해야 한다. 실질적인 지렛대는 쌍대 설계다. 과제별 차이 dᵢ의 평균과 t-구간을 보고하고, 1회 실행이면 McNemar 정확 검정을 쓴다. 50개 중 45개에서 두 설정이 일치하면 사실상 **불일치한 5개가 비교를 결정**한다. Anthropic은 실제 실패에서 뽑은 20~50개 과제가 "훌륭한 출발점"이라고 하지만([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)), 코딩 에이전트에 특화된 최소 과제 수 × 시행 수 표는 어디에도 없었다.

## 모델을 고정하고 하니스만 바꾸면 비용은 최대 100배 움직이지만 정확도는 노이즈 수준이다

2024년의 초기 연구는 인터페이스 설계가 결과를 크게 바꿀 수 있음을 보였다. SWE-agent에서 린터가 붙은 편집 명령을 빼자 Lite 해결률이 **18.0%에서 10.3%**로 떨어졌고, 전체 파일 뷰어(12.7%)는 100줄 창(18.0%)보다 나빴다([SWE-agent](https://arxiv.org/pdf/2405.15793), 스니펫 수준). Aider는 편집 형식을 unified diff로 바꾸는 것만으로 GPT-4 Turbo의 "게으름" 벤치마크 점수가 약 20%에서 61%가 되었다고 보고했다([Aider](https://aider.chat/docs/unified-diffs.html)). oh-my-pi의 hashline 저자는 16개 모델 × 3개 편집 도구를 비교했고, Grok Code Fast 1의 편집 성공률이 6.7%에서 68.3%로 올랐다고 보고했다([blog.can.ac](https://blog.can.ac/2026/02/12/the-harness-problem), 스니펫 수준). 그러나 LSP 피드백 없이 수행한 소규모 독립 재현은 "현세대 모델에서 편집 형식은 병목이 아니다"라고 결론 내렸고, 원 결과에 LSP 피드백 루프가 교란 변수로 섞였을 가능성을 지적했다([DEV 재현](https://dev.to/nwyin/hashline-vs-replace-does-the-edit-format-matter-15n2)). 한편 bash만 쓰는 약 100줄짜리 mini-SWE-agent는 최신 모델로 Verified에서 **70~74% 이상**을 기록했다([mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)). 무거운 스캐폴드가 주던 가치의 상당 부분이 모델 쪽으로 옮겨갔다는 신호다.

2026년의 통제된 연구들은 이 그림을 정리한다. "What Does a Harness Buy? Tokens, Mostly"는 같은 모델, 같은 과제, 같은 가격표로 실험했다. 하니스 간 과제당 비용은 **최대 3배** 달랐고, 잡음을 넘은 유일한 하니스 효과는 *손실*(OpenCode 최대 9pp 열세)이었다. 하니스를 바꿨을 때 결과가 뒤집힌 과제 비율은 같은 하니스를 재실행했을 때와 **똑같이 13%**였다. 첫 호출 프리앰블은 Claude Code가 16,581토큰, OpenCode가 7,025토큰, mini-SWE-agent가 829토큰이었다([arXiv 2610.04433](https://arxiv.org/abs/2610.04433), 스니펫 수준, 판본 간 수치 차이 가능). "The Scaffold Effect"는 Terminal-Bench Pro 50개 과제에서 **토큰 비용 40배 차이, 통과율 차이는 최대 8pp**를 보고했다([arXiv 2607.22585](https://arxiv.org/html/2607.22585v1), 스니펫 수준). MIT FutureTech는 HAL 데이터를 분석해 스캐폴드에 따라 추론 효율이 **약 100배** 달라지고, 같은 스캐폴드가 어떤 모델에는 도움이 되고 다른 모델에는 해가 된다고 정리했다([MIT FutureTech](https://mitfuturetech.substack.com/p/just-a-wrapper-how-much-do-scaffolds)). 반대 증거도 있다. Terminal-Bench 리더보드 스냅샷에서는 Opus 4.6이 Claude Code에서 58.0%, ForgeCode에서 81.8%를 기록해 같은 모델 격차가 15~25pp에 이른다([Vaughan](https://codex.danielvaughan.com/2026/04/09/harness-performance-terminal-bench/), 2차 집계). 하지만 이런 스냅샷은 타임아웃, 재시도, 추론 강도, 벤치마크 맞춤 튜닝이 모두 섞인 상한값으로 읽어야 한다. 채점기 오류 자체가 격차를 만들기도 한다. HAL TAU-bench에서 13pp로 보였던 스캐폴드 격차가 일관된 재채점 후 동률로 사라졌다([arXiv 2611.04399](https://arxiv.org/pdf/2611.04399), 스니펫 수준). Terminal-Bench 저자들이 Claude Code나 Codex CLI 같은 벤더 CLI는 "적절한 과학적 측정 도구가 아니"라며 중립 하니스 Terminus를 따로 만든 이유도 여기에 있다([tbench.ai](https://www.tbench.ai/terminus)).

맥락은 적을수록 낫다는 증거도 쌓이고 있다. AGENTS.md 같은 컨텍스트 파일은 과제 성공률을 *낮추는* 경향이 있었고 추론 비용을 20% 이상 올렸다. 사람이 쓴 파일조차 평균 약 4%의 미미한 이득에 그쳤다. 원인은 행동 변화다. 이런 파일이 에이전트에게 더 넓은 탐색과 테스트를 유도한다([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). 도구 수가 10개에서 100개로 늘면 모든 모델에서 정확도가 약 10pp 떨어졌다([arXiv 2602.23367](https://arxiv.org/pdf/2602.23367)). 다만 *시스템 프롬프트 길이* 하나만 분리한 통제 연구와 서브에이전트 on/off 연구는 찾지 못했다.

비용 측정의 표준은 Kapoor 등이 정했다. 정확도와 비용을 함께 Pareto 프런티어로 보고하고, 가격은 바뀌므로 달러와 함께 **원시 토큰 수**를 남겨야 한다([arXiv 2407.01502](https://arxiv.org/html/2407.01502v1)). HAL은 2만여 회 롤아웃으로 이 방식을 적용했는데, 일부 스캐폴드에서는 캐싱 비용 회계가 불완전했다고 스스로 밝힌다([HAL](https://arxiv.org/pdf/2510.11977)). 캐시 적중률은 cache_read / (cache_read + cache_creation + 비캐시 input)로 정의해야 한다. **캐시 쓰기를 빼면 적중률이 부풀려진다**([DEV](https://dev.to/amitrix/prompt-caching-is-a-harness-design-problem-not-an-api-toggle-2c2b)). 코딩 에이전트 트레이스 연구는 토큰 가중 prefix 적중률이 약 95.7%라고 보고했다([arXiv 2606.30560](https://arxiv.org/pdf/2606.30560), 단일 프리프린트). 시스템 프롬프트에 들어간 타임스탬프나 세션 ID, 도구 정의의 JSON 키 순서 변경이 캐시를 깨뜨린다는 실무 보고도 있다(미검증, [DEV](https://dev.to/esengine/the-boring-secret-to-a-cheap-ai-coding-agent-a-byte-stable-prompt-prefix-5f7k)). Claude Code 문서도 시스템 프롬프트를 바꾸면 캐시 전체가 무효화된다고 명시한다([Claude Code docs](https://code.claude.com/docs/en/prompt-caching.md)). **prefix 안정성을 전용 지표로 측정하는 공개 도구는 찾지 못했다.** 이 점에서 choco-pi prefix-eval의 구조적 prefix 재작성 측정은 공개 관행보다 앞서 있다.

## Calliopi는 prefix-eval을 뼈대로 격리·반복·쌍대 비교를 덧붙이면 된다

### 두 레퍼런스의 위치

Calliopi가 참고할 두 레퍼런스는 업계 스펙트럼의 양 끝에 있다. choco-pi의 prefix-eval은 fixture 저장소 위에서 `pi -p`를 돌리고, tasks.json의 결정적 판정(fileUnchanged, fileContains, finalMessageMatches, 명령 종료 코드, testPattern)으로 채점한다. 시스템+도구 prefix 크기, 구조적 prefix 재작성, 토큰, 비용, 캐시 적중률을 재며, 모델을 다시 부르지 않고 재판정할 수 있다. oh-my-pi의 metaharness는 experiments → arms → runs → traces를 SQLite와 대시보드로 관리하고, 그 아래에 Harbor, 편집 벤치마크, snapcompact를 둔다. 외부 증거에 비추면 Calliopi의 질문, 즉 "확장 X가 같은 모델에서 무엇을 바꾸는가"에 맞는 쪽은 prefix-eval이다. 이유는 세 가지다. 하니스 효과가 가장 확실하게 드러나는 곳이 비용·토큰·캐시인데, prefix-eval은 이미 그것을 잰다. 결정적 판정은 업계가 권고하는 코드 기반 채점기와 같다([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). 재판정 기능은 채점기 결함이 발견될 때(앞서 본 31%, 59.4%의 교훈) 모델 비용 없이 과거 결과를 고칠 수 있게 해 준다. metaharness식 SQLite와 대시보드는 실험이 수십 개로 늘어난 뒤에 도입해도 늦지 않다.

### prefix-eval에 더할 다섯 가지

외부 벤치마크의 실패에서 배워 덧붙일 것은 다섯 가지다.

**첫째, 시행별 격리와 이력 제거.** 시행마다 fixture를 새 임시 디렉터리나 `git worktree`로 복사하고, `.git`은 단일 커밋으로 압축한다. remote, tag, reflog도 지운다. Anthropic의 이전 시행 이력 누출 사례와 `git log --all` 사례에 직접 대응하는 조치다.

**둘째, 판정 스크립트의 보호.** testPattern이나 명령 판정이 쓰는 테스트 파일은 작업 공간 밖에 두었다가 검증 시점에만 복사한다(Harbor의 `/tests` 방식). 아니면 체크섬을 판정에 포함한다. 동시에 세션 JSONL에서 `git log --all`, `git show`, 테스트 파일 쓰기, skip 삽입을 정규식으로 스캔해 "해킹 의심률"을 별도 지표로 남긴다([arXiv 2607.26819](https://arxiv.org/pdf/2607.26819)).

**셋째, 과제 단위 위생 검사.** 과제마다 참조 해답을 넣어 **오라클 실행은 1점, 아무것도 하지 않는 no-op 실행은 0점**이 나오는지 CI에서 확인한다. Terminal-Bench의 오라클 에이전트와 같은 원리이며, Anthropic이 말하는 "pass@100이 0%면 과제가 고장 난 것"을 사전에 걸러낸다. 과제 세트에는 버전을 붙여, 판정을 고쳐도 과거 점수가 조용히 바뀌지 않게 한다.

**넷째, 반복과 통계.** arm마다 과제당 k = 3~5회를 돌린다(opencode-bench는 3회, [opencode-bench](https://github.com/sst/opencode-bench)). 같은 시행 기록에서 pass@1 평균, pass^k, 흔들리는 과제(0 < c < n) 목록을 함께 뽑는다. 비교는 반드시 **같은 과제에 대한 쌍대 차이**로 한다. 확장을 켜고 끈 두 arm 사이에서 결과가 뒤집힌 과제 목록을 출력해 사람이 그 트레이스를 직접 읽는다. 과제가 20~40개라면 수치 검정이 잡아내는 것은 큰 효과뿐이다. 이 목록 검토가 실질적인 분석 도구가 된다.

**다섯째, 비용 지표 보강.** 기존 지표에 캐시 쓰기 토큰을 포함한 적중률, 해결 과제당 비용(총비용 ÷ 성공 수), 비용의 중앙값과 p90(폭주 궤적 때문에 꼬리가 두껍다), 턴 수, 도구 호출 수, 도구 오류율, 시스템 프롬프트+도구 스키마의 해시(prefix 지문)를 추가한다. 가격표와 날짜를 함께 기록해 나중에 재가격 계산을 할 수 있게 한다.

### 어블레이션 프로토콜

어블레이션은 업계가 합의한 통제 조건을 그대로 따른다. 모델, 버전, 추론 강도, 제공자, 타임아웃, 머신 자원을 고정한다. 기준선은 확장이 없는 순수 Pi로 하고, **한 번에 확장 하나만** 켠다. 두 arm의 실행 순서는 시간상 번갈아 배치해 제공자 쪽 변동이 한 arm에 몰리지 않게 한다. 하니스 효과는 모델마다 다르므로([MIT FutureTech](https://mitfuturetech.substack.com/p/just-a-wrapper-how-much-do-scaffolds)), 단일 모델 결과를 일반화하지 말고 결과 행에 모델을 함께 기록한다. 과제 세트를 만들 때는 Hamel Husain의 오류 분석 루프를 쓴다. 실제 Pi 세션 30~50개를 읽어 실패 유형을 분류하고, 유형마다 재현 과제 2~5개를 만든다([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)). 개선된 과제는 회귀 세트로 옮긴다. 공개 저장소에는 올리지 않는 비공개 홀드아웃 몇 개를 따로 유지한다. LLM 판정은 쓰지 않는 것을 기본으로 한다. 꼭 필요하면 pass율과 분리된 별도 점수로만 보고한다. 외부 기준점이 필요할 때는 `badlogic/pi-terminal-bench` 어댑터로 Terminal-Bench 2.x 소규모 부분집합을 Harbor에서 가끔 돌리는 정도면 충분하다([pi-terminal-bench](https://github.com/badlogic/pi-terminal-bench)).

| 결정 항목 | 권고 | 근거가 된 외부 관행 |
|---|---|---|
| 러너 | prefix-eval 확장(자체 TS, `pi -p`) | 결정적 코드 채점기, 재판정 가능성 |
| 격리 | 시행별 임시 복사 + `.git` 압축 | git 이력 누출 33/38건, 시행 간 이력 누출 |
| 판정 보호 | 테스트를 검증 시점에만 복사, 트레이스 해킹 스캔 | Harbor `/tests`, METR·Cursor 사례 |
| 과제 위생 | 오라클=1, no-op=0 CI 검사, 세트 버전 관리 | TB 오라클 에이전트, TB 2.0→2.1 |
| 반복 | arm당 k=3~5, pass@1·pass^k·흔들림 과제 | 단일 실행 2~6pp 변동 |
| 비교 | 과제 단위 쌍대 차이 + 뒤집힌 과제 트레이스 검토 | Miller 쌍대 분석, McNemar |
| 비용 | 캐시 쓰기 포함 적중률, 해결당 비용, p90, prefix 해시 | Kapoor Pareto, HAL 캐시 회계 공백 |
| 외부 기준 | 가끔 pi-terminal-bench로 TB 부분집합 | Harbor 생태계 |

### 확인되지 않은 것

몇 가지는 아직 확인되지 않았다. `pi -p`에 세션 출력 디렉터리 지정 플래그나 JSON 출력 옵션이 있는지, Pi JSONL이 메시지마다 cacheRead/cacheWrite 사용량을 기록하는지는 실제 세션 파일과 `--help`로 확인해야 한다([pi-coding-agent README](https://unpkg.com/@mariozechner/pi-coding-agent@0.73.1/README.md)). `@mariozechner/pi-coding-agent` 패키지가 새 스코프로 이전되었다는 보고도 미검증이다. Harbor의 `-k` 플래그 의미와 네트워크 격리 기본값도 1차 문서로 확인하지 못했다.

## 결론

외부 증거를 종합하면 Calliopi의 확장 평가가 할 일이 바뀐다. 확장이 "정답률을 올리는가"는 20~40개 과제 규모에서 거의 판별할 수 없다. 통제된 연구에서도 하니스의 정확도 효과는 재실행 잡음과 같은 크기였다. 반면 **토큰, 캐시 안정성, 턴 수는 하니스가 확실히 움직이는 변수**다. 이 변수는 시행당 분산이 작아 적은 과제로도 측정된다. 따라서 Calliopi의 평가는 1차 지표를 "같은 성공률에서 비용과 prefix 안정성을 얼마나 지키는가"로 두고, 성공률은 회귀 방지용 하한선으로 다루는 편이 증거와 맞는다. 최소 프롬프트를 선호하는 저자의 직관도 AGENTS.md와 프리앰블 크기 연구가 뒷받침한다. 이제 그 직관을 확장마다 prefix 해시와 쌍대 비용 차이로 증명할 수 있다.

두 번째 함의는 Calliopi가 가장 경계할 대상이 모델이 아니라 **자기 자신의 채점기**라는 점이다. 업계 최고 벤치마크들도 3분의 1 가까이 결함을 안고 출시되었다. 그러니 1인 프로젝트의 tasks.json이 처음부터 옳을 가능성은 낮다. 오라클/no-op 검사, 판정 버전 관리, 재판정, 뒤집힌 과제의 트레이스 읽기는 부가 기능이 아니라 평가 결과를 믿을 수 있게 만드는 핵심 장치다. prefix-eval이 이미 재판정을 지원한다는 점은 이 방향에 가장 유리한 출발점이다.
