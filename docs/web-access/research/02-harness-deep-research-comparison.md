# 딥 리서치를 내장한 하네스는 둘뿐이다

조사한 13개 계열 가운데 이름 붙은 일급 딥 리서치 기능을 싣고 있는 것은 **Claude Code의 `/deep-research` 워크플로와 GitHub Copilot CLI의 `/research` 명령 둘뿐**이다. Gemini CLI는 구글의 호스티드 Deep Research 에이전트를 부르는 커뮤니티 확장에 기대고, 나머지(Codex CLI, OpenCode, Amp, Cursor, Factory Droid, Cline·Roo·Kilo, Goose, Aider, OpenHands, Crush)는 검색·페치·서브에이전트라는 부품만 주고 리서치 루프는 사용자와 커뮤니티에 맡긴다. 웹 도구의 구도는 거의 같다. 검색은 벤더나 모델 프로바이더의 서버가 맡고, 페치는 로컬 HTTP와 마크다운 변환으로 처리하며, 격리된 컨텍스트의 서브에이전트가 요약만 돌려준다. 하네스 사이의 실제 차이는 네 가지 선택에서 나온다. 검색 비용을 누가 내는가, 페이지 원문과 소형 모델의 요약 중 무엇을 메인 컨텍스트에 넣는가, 중간 결과를 리드의 컨텍스트·파일·스크립트 변수 중 어디에 두는가, 리서치를 수동으로만 시작하게 하는가다. 리서치 1회당 토큰이나 금액을 공개한 하네스는 없고, 하네스 간 리서치 품질을 비교한 독립 벤치마크도 찾지 못했다. calliopi에 대해서는 앞선 조사의 3층 권고(버전을 고정한 `pi-web-access` 또는 내장 MCP+Exa, 온디맨드 브라우저 스킬, 작은 로컬 리서치 러너)가 이번 비교에서도 유지된다. 달라지는 것은 러너의 형태와 순서다. 병렬 팬아웃보다 먼저 Crush·OpenHands식의 "웹 전용 리프 연구자 한 명"을 만들고, 시작은 수동 명령으로만 하며, 검색 예산과 "미검증" 표기를 코드로 고정하는 쪽을 권한다.

근거 등급은 다음과 같이 표기한다. **【검증】** 은 2026-11-26에 저장소 소스, docs-as-code, 공식 문서 페이지, npm 메타데이터를 직접 읽은 내용이다. **【스니펫】** 은 검색 결과 요약이나 2차 자료로만 본 내용이다. **【추론】** 은 조사자의 해석이다. 이 조사 환경에서는 ampcode.com, cursor.com, docs.cursor.com, forum.cursor.com, docs.factory.ai, developers.openai.com, ai.google.dev 등이 네트워크 정책으로 차단되었다. 그래서 **Amp와 Cursor 항목은 거의 전부 스니펫**이고, Codex와 Gemini는 문서 사이트 대신 저장소 소스를 읽었다. 공식 문서는 날짜 없는 상시 갱신 페이지이므로 모든 서술은 이 날짜의 상태다.

## 검색은 벤더 서버가 맡고 페치는 로컬 HTTP가 맡는다

검색 백엔드는 누가 호스팅하고 누가 비용을 내느냐에 따라 다섯 갈래로 나뉜다. 첫째는 모델 프로바이더의 서버사이드 검색이다. Claude Code의 WebSearch는 Anthropic `web_search` 서버 도구의 얇은 래퍼이며 문서는 "검색 백엔드는 설정할 수 없다. 다른 프로바이더로 검색하려면 MCP 서버를 추가하라"고 적는다【검증】([Claude Code 도구 레퍼런스](https://code.claude.com/docs/en/tools-reference)). Codex CLI는 Responses API의 호스티드 `web_search`를 쓰고, Gemini CLI는 Flash 유틸리티 모델에 `googleSearch` 그라운딩을 켠 중첩 호출을 쓰며, Cline은 "내장 웹 검색이 있는 프로바이더만 이 설정을 따른다"고 적는다【검증】([codex hosted_spec.rs](https://github.com/openai/codex/blob/af71942309704997f4bdc86c020717646423c080/codex-rs/core/src/tools/hosted_spec.rs), [gemini-cli web-search.ts](https://github.com/google-gemini/gemini-cli/blob/60f8082b14ffa7f10b608270232f3f57b5abbec8/packages/core/src/tools/web-search.ts), [Cline Desktop 문서](https://github.com/cline/cline/blob/main/docs/usage/cline-desktop.mdx)). 둘째는 하네스 벤더가 자기 계정 뒤에서 검색을 대신 호스팅하는 키 없는 방식으로, Factory Droid, Copilot CLI, Kilo의 Exa 프록시, OpenCode Console의 건당 0.01달러 검색이 여기에 든다. 셋째는 사용자 키로 프로바이더를 고르는 방식(OpenCode V2의 5개 프로바이더, OpenHands의 Tavily MCP)이다. 넷째는 DuckDuckGo 무료 스크레이핑(Crush, Goose 기본값)이다. 다섯째는 검색이 아예 없는 경우(Aider, 종료 시점의 Roo Code)다. 세 번째 이하의 분류는 대부분 저장소 소스에서 직접 읽은 사실이고, 다섯 갈래로 묶은 것은 조사자의 정리다【추론】.

페치는 구현이 훨씬 비슷하다. 대부분 로컬 HTTP GET 뒤에 HTML을 마크다운으로 바꾸고 일정 길이에서 자른다. 차이는 그 결과를 메인 모델이 그대로 읽느냐, 소형 모델이 먼저 읽고 답만 넘기느냐에 있다.

표에서 세 가지 세부가 눈에 띈다. 첫째, Codex의 기본 모드 `cached`는 호스티드 도구에 `external_web_access: false`를 보낸다. 라이브 검색은 `--search` 플래그나 `web_search = "live"` 설정으로 켜고, 샌드박스를 끈 풀 액세스 프로필에서는 조건이 맞으면 자동으로 `live`로 승격된다【검증】([core/src/config/mod.rs](https://github.com/openai/codex/blob/af71942309704997f4bdc86c020717646423c080/codex-rs/core/src/config/mod.rs)). 캐시가 OpenAI가 유지하는 인덱스라는 설명은 차단된 공식 문서의 스니펫에서만 보았다【스니펫】([Codex 설정 문서](https://developers.openai.com/codex/config-basic)). 신선도가 가장 느슨한 샌드박스 설정에 묶여 있다는 뜻이므로, 리서치 용도라면 기본값이 약점이다【추론】.

둘째, Gemini CLI에서는 검색 한 번과 페치 한 번이 각각 별도의 Flash 모델 요청이다. 메인 에이전트는 원시 검색 결과를 보지 못하고 Flash가 쓴 요약만 받는다. 원문을 받는 경로는 실험 설정 `experimental.directWebFetch`(기본 꺼짐)다【검증】([configuration.md](https://github.com/google-gemini/gemini-cli/blob/60f8082b14ffa7f10b608270232f3f57b5abbec8/docs/reference/configuration.md)).

셋째, OpenCode에 대한 "Exa 검색은 Zen 사용자나 `OPENCODE_ENABLE_EXA`에서만 열린다"는 통설은 V1(v1.3.0 태그)에만 맞다. V2에서는 첫 사용 시 동의와 프로바이더 선택으로 바뀌었다. 다만 Exa 프로바이더는 여전히 `https://mcp.exa.ai/mcp`를 호출하고 자격 증명이 있을 때만 키를 붙이므로, 키 없는 경로가 코드에 남아 있다【검증】([registry.ts v1.3.0](https://github.com/anomalyco/opencode/blob/v1.3.0/packages/opencode/src/tool/registry.ts), [exa.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/websearch/exa.ts)).

브라우저 자동화는 전반적으로 후퇴하고 있다. Roo는 브라우저 도구를 통째로 제거했고, Goose의 Computer Controller에는 더 이상 `web_scrape`가 없으며, OpenHands는 CLI 모드에서 브라우저를 끈다. Gemini CLI의 `browser_agent`는 기본 비활성이고 Kilo는 Playwright MCP를 선택 사항으로 둔다【검증】([Goose computercontroller](https://github.com/block/goose/blob/main/crates/goose-mcp/src/computercontroller/mod.rs), [Gemini 서브에이전트 문서](https://github.com/google-gemini/gemini-cli/blob/60f8082b14ffa7f10b608270232f3f57b5abbec8/docs/core/subagents.md)). 브라우저는 "항상 켜진 도구"에서 "필요할 때 붙이는 옵션"으로 옮겨 갔다【추론】.

## 서브에이전트는 어디에나 있고 스크립트 워크플로는 Claude Code에만 있다

리서치 팬아웃의 기본 단위는 하네스마다 같다. 자기 컨텍스트 창을 가진 서브에이전트가 일하고 최종 메시지 하나만 부모에게 돌려준다. 다른 것은 중첩 깊이, 동시성, 백그라운드 여부, 그리고 서브에이전트가 웹 도구를 실제로 받느냐다. 구조는 세 단으로 나뉜다. 가장 흔한 것은 부모가 직접 분해해 일반 서브에이전트를 부르는 "범용 팬아웃"이다. 두 번째는 웹 전용 도구 세트와 출처 계약을 가진 격리 에이전트 하나를 도구처럼 부르는 "리프 연구자"로, Crush의 `agentic_fetch`와 OpenHands의 `web-researcher`가 해당한다. 세 번째는 모델 컨텍스트 밖의 스크립트가 루프와 중간 결과를 쥐는 방식이고, 이를 제공하는 것은 Claude Code의 동적 워크플로뿐이다. 세 단으로 나눈 것은 조사자의 분류다【추론】.

Claude Code의 워크플로가 다른 단계에 놓이는 이유는 중간 결과의 위치다. 공식 문서는 "워크플로 스크립트가 루프와 분기와 중간 결과를 직접 쥐므로 Claude의 컨텍스트에는 최종 답만 남는다"고 쓰고, 서브에이전트에 대해서는 반대로 "상세한 결과를 돌려주는 서브에이전트가 많으면 메인 컨텍스트가 그래도 찬다"고 경고한다【검증】([워크플로](https://code.claude.com/docs/en/workflows), [서브에이전트](https://code.claude.com/docs/en/sub-agents)). 서브에이전트 격리는 작업자의 컨텍스트만 보호하고 리드의 컨텍스트는 보호하지 못한다. 커뮤니티 스킬이 "노트를 파일에 쓰고 경로만 돌려준다"는 규약으로 수렴한 것은 이 압력 때문으로 보인다【추론】. Anthropic의 Agent SDK 리서치 데모도 연구자 서브에이전트가 결과를 `files/research_notes/`에 저장한다【검증】([research-agent 데모](https://github.com/anthropics/claude-agent-sdk-demos/tree/main/research-agent)).

리프 연구자 패턴에서는 프롬프트가 설계의 대부분이다. OpenHands의 `web-researcher`는 Tavily, 페치, 브라우저 순의 도구 사다리와 "막힌 사이트에 2회 이상 쓰지 말 것", "핵심 사실은 독립 출처 2개 이상으로 교차 확인", "모든 주장에 출처 URL", "과정 중계 금지"를 규정한다. Crush의 `agentic_fetch`는 소형 모델과 고정 도구 세트(`web_fetch`, `web_search`, `glob`, `grep`, `sourcegraph`, `view`)로 임시 디렉터리에서 돌고, 3~6단어의 작은 검색을 여러 번 하라는 지시와 말미의 `Sources` 절을 요구한다【검증】([web_researcher.md](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-tools/openhands/tools/preset/subagents/web_researcher.md), [agentic_fetch_prompt.md.tpl](https://github.com/charmbracelet/crush/blob/main/internal/agent/templates/agentic_fetch_prompt.md.tpl)).

내장한 두 곳도 성격이 다르다. Claude Code의 `/deep-research`는 범용 웹 리서치다. 스크립트가 구조화 출력과 주장 단위 투표를 강제하지만, 실제 스크립트(단계 목록, 에이전트 수, 단계별 모델, 주장당 검증자 수)는 공개되지 않았고 문서 색인에도 워크플로 페이지 안에만 등장한다【검증】([문서 색인](https://code.claude.com/docs/llms.txt)). Copilot의 `/research`는 코드 증거 쪽으로 치우쳐 있다. 문서가 밝힌 지침은 "문서보다 코드를 우선하고 파일 경로와 줄 번호를 제시", "공개 대안보다 조직 내부 구현을 우선"이다. 리서치 모델은 고정이어서 `/model`로 바꾸지 못하고, 리서치는 코드를 변경하지 않는다【검증】([리서치 문서](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-cli/use-copilot-cli/research-with-copilot-cli.md)). 내장 에이전트 표의 `research`가 claude-haiku-4.5로 적혀 있으므로 값싼 작업자와 별도 오케스트레이터의 구성일 가능성이 높다. 오케스트레이터 모델과 병렬 수는 문서에 없다【추론】. Copilot의 리서치는 "Amp의 Librarian에 보고서 작성기를 붙인 것"에 가깝고, 출처 품질을 따지는 범용 웹 딥 리서치를 설계 목표로 밝힌 곳은 Claude Code 하나다【추론】.

두 벤더 모두 딥 리서치를 **명시적 수동 호출**로 묶었다. Claude Code는 v2.1.218에서 "`/deep-research`는 수동 호출 시에만 시작하며 Claude가 스스로 띄우지 않는다"로 바꿨다【검증】([Claude Code CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). 커뮤니티 쪽도 같다. OpenCode 최대의 커뮤니티 계층이던 oh-my-opencode는 `ulw-research` 스킬(병렬 explore·librarian 스웜, 인용 종합)에 대해 "의도적으로 명시적이며 일반 질문은 포화 스웜을 발동하지 않는다"고 적는다【검증】([OmO features.md](https://github.com/code-yeongyu/oh-my-openagent/blob/HEAD/docs/reference/features.md)). 이 프로젝트는 현재 README가 스스로를 "pi의 포크인 senpi 위에서 도는 `omo` 명령"으로 소개한다. OpenCode 생태계에서 가장 큰 리서치 계층이 pi 계열로 넘어온 셈이다【검증】([OmO README](https://github.com/code-yeongyu/oh-my-openagent/blob/HEAD/README.md)).

Claude Code 커뮤니티 스킬은 내장 기능이 있어도 여전히 크다. `hyperresearch`(별 5,115)는 16단계 파이프라인, SQLite 색인 노트 볼트, 역할별 모델 배정, `[Read, Edit]`로 도구를 잠근 패처, 인용-문장 결속 표본 검사를 갖췄고, `claude-deep-research-skill`(별 1,229)은 8단계 파이프라인과 디스크에 저장하는 `sources.json`, 인용 검증 스크립트를 쓴다. 다만 품질과 벤치마크 수치는 전부 작성자의 자기 보고다【검증, 자기 보고】([hyperresearch](https://github.com/jordan-gibbs/hyperresearch), [claude-deep-research-skill](https://github.com/199-biotechnologies/claude-deep-research-skill)). 이 무거운 스킬들이 내장 WebSearch·WebFetch를 자체 검색 CLI나 Exa·Tavily·Firecrawl로 대체하거나 보강한다는 점은, 변경 불가능한 백엔드와 세션 검색 예산과 손실 있는 요약 페치가 넓은 조사에는 부족하다는 사용자 판단을 시사한다【추론】.

## 비용 수치는 거의 없고 함정은 변경 로그에 남아 있다

공개된 정량 수치는 Anthropic 것이 거의 전부이고 그마저 Claude Code를 측정한 값이 아니다. 2025년 6월 엔지니어링 글은 claude.ai Research에 대해 에이전트가 채팅의 약 4배, 멀티에이전트가 약 15배의 토큰을 쓴다고 했고, 내부 평가에서 Opus 4 리드와 Sonnet 4 서브에이전트 구성이 단일 에이전트보다 90.2% 높았다고 보고했다【검증】([Anthropic 엔지니어링](https://www.anthropic.com/engineering/multi-agent-research-system)). Claude Code 문서의 수치는 에이전트 팀이 표준 세션의 약 7배 토큰을 쓴다는 것, API 과금에서 검색 1,000회당 10달러가 붙는다는 것, 100kB 문서 페이지가 약 25,000토큰이라는 것이다【검증】([비용 문서](https://code.claude.com/docs/en/costs), [웹 검색 도구](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [웹 페치 도구](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)). 그 밖에 문서화된 단가는 OpenCode Console의 검색당 0.01달러뿐이다【검증】([console/websearch.mdx](https://github.com/anomalyco/opencode/blob/dev/services/site/src/docs/content/console/websearch.mdx)). 구글 호스티드 Deep Research의 작업당 약 2달러(Max는 약 5달러)라는 추정은 제3자 글에만 있고 구글 포럼 글과 일부 어긋난다【스니펫】([tokencost.app](https://tokencost.app/blog/gemini-deep-research-agent-cost), [구글 AI 포럼](https://discuss.ai.google.dev/t/google-gemini-deep-research-costs/112804)).

비용 통제 장치는 다섯 종류가 반복된다. 첫째는 **페이지 절단과 파일 스필**이다. Goose 15,000자, Copilot 20,000자 페이징, Cline 50,000자, Crush 50KB 초과분 임시 파일, OpenCode의 관리 저장소 보관이 그 예이고, Aider만 절단이 없다. 둘째는 **소형 모델 사전 독해**다. Claude Code의 Haiku `web-fetch`, Gemini의 Flash, Crush의 small model이 해당하고, Cursor의 `explore`가 더 빠른 모델을 쓴다는 것은 스니펫에만 근거한다. 셋째는 **서브에이전트 격리와 짧은 반환**이며, Copilot `explore`의 "300단어 이내 답"이 대표적이다. 넷째는 **호출 예산**이다. Claude Code는 폭주 검색 루프를 막으려고 세션당 WebSearch 200회 한도를 넣었다가 시간당 100회 리필 방식으로 바꿨고, 이 예산은 메인 대화와 서브에이전트가 공유한다. Gemini CLI는 일일 요청 한도(무료 API 키 250회, 계정 요금제별 1,000~2,000회)를 문서화하는데 검색과 페치도 각각 모델 요청이라 이 한도를 함께 쓴다. 다섯째는 **권고성 규모 경고**로, Claude Code 워크플로는 에이전트 25개나 예상 150만 토큰을 넘으면 경고하지만 실행을 멈추지는 않는다【검증】([Claude Code 도구 레퍼런스](https://code.claude.com/docs/en/tools-reference), [워크플로](https://code.claude.com/docs/en/workflows), [Gemini 쿼터 문서](https://github.com/google-gemini/gemini-cli/blob/60f8082b14ffa7f10b608270232f3f57b5abbec8/docs/resources/quota-and-pricing.md), [Copilot 명령 레퍼런스](https://github.com/github/docs/blob/main/content/copilot/reference/copilot-cli-reference/cli-command-reference.md)). 대화형 리서치 1회에 강제되는 토큰·금액 상한을 문서화한 하네스는 없다【추론】.

프롬프트 인젝션에 대한 방어는 층이 얇고 하네스마다 다르다. Gemini CLI는 웹 출력 전체를 `<untrusted_context>`로 감싸고 닫는 태그를 이스케이프한다. Claude Code는 대부분의 페치에서 별도 모델 호출의 답만 전달하고, 서브에이전트 보고에서 지시문처럼 보이는 텍스트를 스캔하며, 자동 모드에서는 분류기가 페치를 심사한다. 그러면서도 "어떤 시스템도 모든 공격에 완전히 면역은 아니다"라고 명시한다【검증】([textUtils.ts](https://github.com/google-gemini/gemini-cli/blob/60f8082b14ffa7f10b608270232f3f57b5abbec8/packages/core/src/utils/textUtils.ts), [Claude Code 보안 문서](https://code.claude.com/docs/en/security)). Crush와 OpenHands는 웹 콘텐츠를 셸·쓰기 도구가 없거나 좁은 서브에이전트로 먼저 통과시킨다. Cline과 Kilo는 페치한 텍스트를 셸과 편집 도구를 쥔 메인 에이전트의 컨텍스트에 바로 넣고, Goose는 `curl` 출력을 메인 에이전트의 셸로 받는다. 이 일곱 하네스에서 읽은 파일 가운데 콘텐츠 정제나 인젝션 탐지 단계를 서술한 것은 없었다【추론】. 인용 정확성도 도구가 보장하지 않는다. Claude Code의 하네스 도구는 API의 네이티브 인용 객체를 노출하지 않으므로 보고서의 인용은 모델이 쓴 URL이고, 그래서 내장 워크플로와 커뮤니티 스킬 모두 별도의 검증 패스를 둔다【추론】.

## 설계 선택지는 여덟 개의 축으로 정리된다

하네스들의 공통점은 세 가지다. 첫째, 검색 도구 하나, 페치 도구 하나, 요약만 돌려주는 격리 서브에이전트라는 삼각 구성이 사실상 표준이다. 둘째, 일급 딥 리서치를 만든 벤더는 모두 그것을 수동 호출, 디스크에 저장되는 보고서, 값싼 작업자 모델, 별도 검증 단계와 묶었다. 셋째, 코드 중심 조사(다른 저장소 읽기)는 범용 웹 조사와 별개의 능력으로 취급된다. Amp의 Librarian, Copilot의 `research` 에이전트, OmO의 librarian과 grep.app, Crush의 `sourcegraph` 도구가 그 예다. 아래 표는 하네스들이 갈라지는 지점을 선택지로 정리한 것이다. 각 사례는 앞 절의 출처에 근거하고, 축으로 묶은 것과 장단점 평가는 조사자의 종합이다【추론】.

| 축 | 선택지 | 대표 사례 | 얻는 것과 잃는 것 |
|---|---|---|---|
| 검색 호스팅 | 프로바이더 네이티브 / 벤더 호스티드 / 사용자 키 선택형 / 무료 스크레이핑 / 없음 | Claude Code·Codex·Cline / Droid·Copilot·Kilo / OpenCode·OpenHands / Crush·Goose / Aider | 네이티브는 설정이 없지만 모델에 종속(Cline은 Bedrock·로컬 모델에서 검색 없음). 선택형은 자유롭지만 키 관리와 429 대응이 사용자 몫. 스크레이핑은 무료지만 예고 없이 깨짐 |
| 메인 컨텍스트에 넣는 것 | 제목·URL만 / 소형 모델의 답 / 절단한 원문과 스필·페이징 | Claude Code 검색 / Claude Code 페치·Gemini·Crush `agentic_fetch` / OpenCode·Cline·Copilot·Goose | 요약은 컨텍스트와 인젝션 노출을 줄이지만 묻지 않은 내용을 잃음. 원문은 충실하지만 토큰과 인젝션 표면이 큼 |
| 검색 도구의 위치 | 메인 에이전트 직접 / 서브에이전트 전용 / 스킬 로드 후 | 대부분 / Crush / Goose | 서브에이전트 전용은 요약을 강제함. 스킬형은 유휴 스키마 비용이 0이지만 한도가 코드가 아닌 지시문 |
| 팬아웃 구조 | 없음 / 리프 연구자 / 범용 서브에이전트 / 스크립트 워크플로 | Aider / Crush·OpenHands / 대부분 / Claude Code | 뒤로 갈수록 폭과 검증력이 늘고 비용과 실패 지점도 늘어남 |
| 중간 결과의 위치 | 리드 컨텍스트 / 디스크 파일 / 스크립트 변수 / 공유 보드 | 범용 서브에이전트 / Copilot·SDK 데모·커뮤니티 스킬 / Claude Code 워크플로 / Kilo Swarm | 파일은 압축과 재개에 견디고 사람이 검사할 수 있음 |
| 검증 강도 | 없음 / 출처 목록 계약 / 독립 출처 2개 교차 확인 / 주장별 투표와 미검증 표기 | 범용 / Crush / OpenHands / Claude Code | 강할수록 에이전트 호출이 늘어남. "검증 실패"와 "반박됨"을 구분해야 함 |
| 발동 방식 | 모델 자율 / 수동 명령 전용 | 범용 서브에이전트 / `/deep-research`, `/research`, `ulw-research` | 수동 전용은 비용 폭주를 막고 사용자가 기대 시간을 알게 함 |
| 깊은 조사의 소재 | 하네스 루프 안 / 호스티드 에이전트에 위임 | Claude Code·Copilot / Gemini 확장(Interactions API), Codex용 커뮤니티 MCP | 위임은 구현이 없지만 별도 과금·쿼터가 붙고 로컬 파일과 결합이 약함 |

두 번째 축에 대해서는 입장을 정할 수 있다. 소형 모델 요약과 원문 절단은 둘 다 실전에서 쓰이는 방식이다. 그러나 요약 방식을 택한 하네스는 원문으로 가는 탈출구를 반드시 따로 만들어야 했다. Claude Code는 `offset`, Gemini는 `directWebFetch`, Crush는 원문용 `fetch`가 그것이다. 반대로 원문 방식을 택한 하네스는 격리를 서브에이전트에서 얻는다. 리서치의 충실도가 중요하고 연구자를 이미 격리한다면, 페치 계층에서 한 번 더 요약할 이유는 약하다【추론】.

## calliopi는 리프 연구자부터 만들고 수동으로만 시작한다

앞선 pi 조사는 calliopi(현재 웹 도구 없음)에 3층 구성을 권고했다. 1층은 버전을 고정한 `pi-web-access` 또는 내장 MCP에 Exa 호스티드 서버를 붙이는 구성, 2층은 온디맨드 브라우저 스킬, 3층은 프롬프트 템플릿으로 시작해 로컬 `pi` 자식 프로세스 기반의 작은 리서치 러너로 넓히는 구성이다. 같은 조사는 `calliopi-fanout`이 Cursor Cloud Agents를 병렬 생성하는 익스텐션이고 `calliopi-workflows`가 플로팅 터미널 워크플로 모음이어서 리서치 오케스트레이션에 그대로 쓰이지 않는다는 점도 저장소 README로 확인했다【검증: `/home/user/calliopi/packages/calliopi-fanout/README.md`, `/home/user/calliopi/packages/calliopi-workflows/README.md`】. 이번 비교는 이 권고를 뒤집지 않는다. 대신 각 층의 근거를 보강하고 3층의 형태를 구체화한다. 아래 시사점은 모두 추론이며, 명령과 호환성은 이 세션에서 실행해 보지 않았다.

**1층은 "원문, 절단, 세션 밖 저장, 페이징" 계열에 그대로 둔다.** `pi-web-access`의 설계(인라인 30,000자 한도, 세션 밖 캐시, `get_search_content` 페이징, SSRF·리다이렉트 검사)는 Copilot의 20,000자 페이징, Crush와 Goose의 임시 파일 스필, OpenCode의 관리 저장소 보관과 같은 계열이고, 여기서 다수파다【검증】([pi-web-access README](https://github.com/nicobailon/pi-web-access), [Copilot changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). 앞선 조사가 "익스텐션이 스스로 부르는 요약 모델은 꺼 두라"고 한 권고도 유지한다. 요약 독해의 이점인 컨텍스트 절약과 인젝션 완충은 3층의 격리 연구자에서 얻을 수 있고, 그 편이 원문 탈출구를 따로 만들 필요가 없다. pi-ai 1.5.2에는 프로바이더 서버사이드 검색 지원이 없으므로 Claude Code·Codex·Cline식 네이티브 검색은 지금의 calliopi가 택할 수 있는 길이 아니다【검증: 앞선 조사의 로컬 grep】([npm @earendil-works/pi-ai](https://www.npmjs.com/package/@earendil-works/pi-ai)).

대안인 "내장 MCP + Exa"는 이번 조사에서 선례를 얻었다. `mcp.exa.ai`의 키 없는 호스티드 엔드포인트는 OpenCode V1·V2, Kilo, OmO가 기본 검색으로 쓰는 바로 그 백엔드다【검증】([OpenCode exa.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/websearch/exa.ts), [Kilo websearch.ts](https://github.com/Kilo-Org/kilocode/blob/main/packages/core/src/tool/websearch.ts)). 같은 선례가 약점도 알려 준다. OpenCode가 429 쿨다운과 프로바이더 교대를 구현했다는 것은 이 경로가 실제로 속도 제한에 걸린다는 정황이다. 최소 구성으로 가더라도 두 번째 프로바이더나 자가 호스팅 SearXNG로의 폴백 경로를 정해 두는 편이 낫다. Goose와 `pi-web-access`가 모두 SearXNG를 우선순위에 둔다는 점도 로컬 우선 구성을 뒷받침한다. DuckDuckGo 스크레이핑은 Crush와 Goose가 쓰지만 가장 예고 없이 깨질 경로이므로 기본값으로 삼지 않는다.

**2층의 온디맨드 브라우저 스킬 권고는 더 강해졌다.** Roo의 브라우저 제거, Goose의 `web_scrape` 삭제, OpenHands의 CLI 모드 브라우저 비활성, Gemini CLI의 `browser_agent` 기본 비활성은 모두 같은 방향이다. OpenHands의 도구 사다리(검색, 페치, 브라우저는 마지막)와 "막힌 사이트에 2회 이상 쓰지 말라"는 규칙은 브라우저 스킬의 SKILL.md와 연구자 프롬프트에 그대로 옮겨 쓸 만하다.

**3층은 병렬 러너보다 리프 연구자 한 명이 먼저다.** 앞선 권고의 순서는 "직접 모드 프롬프트 템플릿, 그다음 로컬 자식 러너"였다. 이번 비교는 그 사이에 단계 하나를 넣으라고 말한다. 오픈소스 하네스가 실제로 내장한 리서치 기능은 병렬 파이프라인이 아니라 Crush의 `agentic_fetch`와 OpenHands의 `web-researcher`, 곧 웹 전용 도구 세트와 출처 계약을 가진 격리 에이전트 하나였다. calliopi에서는 `pi --mode json -p --no-session` 자식 프로세스 하나에 `read`, `write`와 웹 도구만 허용하고, 값싼 모델을 지정하고, 노트 파일 경로와 한 줄 요약만 돌려받는 도구나 명령이 이에 해당한다. 병렬 팬아웃은 이 단위를 4개까지 동시에 띄우는 얇은 확장으로 남는다. 러너를 만들 때 이번 조사가 더하는 규칙은 다음 여섯 가지다.

첫째, **발동은 수동 명령 전용**으로 한다. Claude Code가 자동 발동을 거둬들였고 OmO도 같은 선택을 했다. 일반 질문은 직접 모드 템플릿으로 처리한다.

둘째, **상한을 코드에 고정한다.** 동시 실행 4, 연구자 2~6명이라는 앞선 수치에 더해 실행당 검색 호출 예산을 둔다. Claude Code가 폭주 검색 루프 때문에 세션 예산을 도입한 전례가 있고, 익명 Exa 한도는 자식 프로세스 전체가 공유한다. 공식 `subagent` 예제에서는 자식의 토큰 사용량이 부모 합계에 더해지지 않으므로, `/cl-usage`에 자식 사용량을 집계해야 리서치 1회의 실제 비용이 보인다.

셋째, **실패를 결과와 구분한다.** 각 자식의 노트 파일이 실제로 존재하는지 확인하고, 검증 패스가 속도 제한이나 오류로 확인하지 못한 주장은 "반박됨"이 아니라 "미검증"으로 표기한다. Claude Code의 v2.1.196 버그와 Goose의 무출력 실패가 바로 이 구분이 없어서 생긴 문제였다.

넷째, **자식이 웹 도구를 실제로 받는지 스모크 테스트한다.** Claude Code, Cline, Cursor가 모두 이 지점에서 문제를 겪었다. pi에서는 별도 `pi` 프로세스가 설치된 익스텐션과 `mcp.json`을 로드하지만, SDK 세션은 내장 익스텐션(MCP, codemode, tool search)을 자동 로드하지 않는다【검증: 로컬 `docs/mcp.md`】.

다섯째, **권한은 도구 목록으로 제한한다.** 연구자에게 `bash`를 주지 않는 앞선 권고는 Crush의 무셸 페치 서브에이전트와 같은 방어이고, 이 표본에서 모델의 주의력에 기대지 않는 유일한 인젝션 완화책이다. 비용이 거의 들지 않는 보강으로 Gemini CLI처럼 웹에서 온 텍스트와 연구자 노트를 리드에게 넘길 때 비신뢰 구획 태그로 감싸는 방법이 있다.

여섯째, **보고서는 세션별 디렉터리에 새 파일로 저장한다.** Copilot의 `~/.copilot/session-state/SESSION-ID/research/` 규약과 덮어쓰기 버그가 근거다. 이 보고서처럼 직접 읽음·스니펫·추론의 등급 표기를 템플릿에 넣는다.

부수적 시사점이 세 가지 더 있다. `calliopi-fanout`은 리서치가 아닌 코드 작업용으로 남겨 두는 편이 맞다. Cursor Cloud Agents에는 세 가지 이그레스 모드가 있고 서브에이전트의 웹 도구가 거부된 보고가 있어, 로컬에 설치한 웹 도구와 파일 기반 노트 규약을 그쪽에서 기대하기 어렵다【스니펫】([Cloud Agents 네트워크 문서](https://cursor.com/docs/cloud-agent/security-network), [포럼 173837](https://forum.cursor.com/t/subagent-unable-to-use-web-fetch-and-search/173837)). 다음으로, 호스티드 딥 리서치 위임은 선택적 4층으로 열어 둘 수 있다. Gemini 확장의 형태(Interactions API를 감싼 MCP 서버)는 pi 내장 MCP에 그대로 붙는 구조다. 다만 유료 키와 별도 쿼터가 필요하고 작업당 비용은 제3자 추정만 있으므로 기본 경로로는 권하지 않는다. 마지막으로, 코드 중심 조사는 웹 리서치와 분리해 다룬다. 다른 저장소를 읽는 일은 Amp·Copilot·Crush처럼 `gh`나 로컬 클론으로 처리하는 편이 낫고, `pi-web-access`가 GitHub URL을 스크레이핑하지 않고 클론이나 `gh`로 돌리는 것도 같은 판단이다. pi 계열의 참고 구현으로는 senpi 위의 OmO `ulw-research`가 새로 생겼지만, 포크 위의 스킬이라 가져다 쓸 부품이 아니라 설계 참고 자료다.

## Conclusion

이 비교가 바꾸는 인식은 "주요 하네스는 딥 리서치를 갖추고 있고 calliopi만 뒤처져 있다"는 전제다. 13개 계열 가운데 11개는 딥 리서치를 내장하지 않았고, 내장한 두 곳도 최근에 넣은 기능을 계속 손보고 있다. Copilot은 2026년 2월에 추가해 5월에 구조를 바꿨고, Claude Code는 출시 시점이 변경 로그에 날짜 없이 남아 있지만 미검증 표기와 자동 발동 같은 기본 동작을 출시 뒤에 고쳤다. 오픈소스 쪽이 실제로 수렴한 지점은 대형 파이프라인이 아니다. 절단과 스필이 있는 페치, 프로바이더를 고를 수 있는 검색, 출처 계약을 가진 리프 연구자 하나다. calliopi의 3층 권고는 이 수렴점과 겹치므로, 빠진 것은 기능이 아니라 한도와 실패 표기와 사용량 집계를 코드로 고정하는 일이다.

권고를 확정하기 전에 닫아야 할 공백은 이번에도 분명하다. Amp와 Cursor 항목은 ampcode.com과 cursor.com을 허용 목록에 넣고 다시 확인해야 한다. 특히 Amp의 웹 검색·페이지 읽기 도구는 이름과 백엔드조차 확인하지 못했다. `/deep-research`와 `/research`의 실행당 토큰과 금액, 그리고 리프 연구자 하나와 병렬 팬아웃의 품질 차이는 어디에도 공개된 측정이 없다. calliopi가 러너를 만든다면 Anthropic이 권한 대로 실제 질의 20개 정도의 소규모 평가 세트를 먼저 만들어 직접 모드, 리프 연구자, 4병렬을 같은 질문으로 비교하는 것이 이 공백을 메우는 가장 싼 방법이다【검증: 평가 권고의 출처】([Anthropic 엔지니어링](https://www.anthropic.com/engineering/multi-agent-research-system)).
