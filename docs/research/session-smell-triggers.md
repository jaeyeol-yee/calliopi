# 세션 중 이상 신호로 개선을 트리거하기: 선례와 제안

2026-11-27 조사. 질문은 "Calliopi가 세션을 진행하면서 이상 신호(red flag, smell)를 감지해 자기개선을 트리거할 수 있는가, 그런 선례가 있는가"다. 판정 기준과 RSI 전반의 경향은 [agent-self-improvement-evidence.md](agent-self-improvement-evidence.md)에 있고, 이 문서는 그중 "무엇이 개선을 시작하게 하는가"만 다룬다. 출처와 읽은 범위는 [부록](#부록-출처와-읽은-범위)에 있다.

3절과 4절은 제안이다. 임계치 숫자를 포함해 저장소 소유자가 확정하기 전까지 결정이 아니다.

## 1. 선례

| 하네스 | 감지 시점 | 감지 방식 | 조치 |
|---|---|---|---|
| choco-pi 스킬 체크 | 도구 호출 시 | 규칙. `commit` 스킬을 읽기 전의 `git commit`, 워크플로 스킬을 읽기 전의 첫 편집 | 도구 결과에 경고를 붙인다. 막지 않고, 컨텍스트당 한 번이다. |
| choco-pi 세션 로그 집계 | 사후 | 수백 개 세션의 모델별 도구 오류율 | 사람이 가이던스와 스키마를 고치고 이력 문서에 남긴다. |
| Devin Session Insights | 세션 종료 시. 큰 세션은 자동 | LLM 분석. 영향도별 이슈 타임라인, 오도한 Knowledge 표시 | 고친 프롬프트와 환경 설정 변경을 제안한다. |
| Devin Knowledge Suggestions | 세션 중 | 사용자의 채팅 피드백 | 기억할 항목을 제안하고, 사람이 고치거나 저장하거나 버린다. |
| Claude Code `/insights` | 수동 | 최근 세션 분석 | 어디서 잘못되는지를 담은 HTML 리포트 |
| Claude Code `/fewer-permission-prompts` | 수동 | 트랜스크립트에서 반복되는 읽기 전용 호출 | 허용 목록을 제안한다. |
| OmO Kibitzer | 세션 중 상주 | 세션 이벤트를 받는 읽기 전용 사이드카 모델 | 넛지만 한다. 파일과 메모리를 쓰지 못한다. |
| OMC `self-improve` 스킬 | 수동 시작 후 자율 루프 | 사용자가 준 벤치마크 점수 | 후보를 만들어 토너먼트로 고른다. 벤치마크 파일은 봉인한다. |

관찰:

- **감지는 자동이고 반영은 사람이 승인한다.** 확인한 제품 가운데 세션 중에 자기 프롬프트를 고쳐 적용하는 것은 없었다. OMC `self-improve`만 자율 루프인데, 대상이 하네스가 아니라 사용자의 코드이고 판정자는 고정된 벤치마크다.
- **감지 방식은 둘로 갈린다.** 결정적 규칙(choco-pi)과 LLM 사후 분석(Devin, Claude Code)이다. 세션 중에 LLM이 판정하는 것은 OmO Kibitzer뿐이고, 문서 설명만 확인했다.
- **가장 흔한 입력은 사용자의 교정이다.** Devin은 채팅 피드백에서 제안을 만들고, Claude Code는 과거 세션을 읽는다. 둘 다 사람이 이미 불편을 표현한 지점에서 출발한다.
- **효과를 측정해 공개한 곳은 없었다.** 넛지나 제안이 결과를 낫게 했다는 수치를 찾지 못했다. choco-pi는 도입 전 위반 사례를 기록했지만 도입 후 수치는 이력에 없다.

## 2. 설계에 영향을 주는 근거

1. **체감은 판정 근거가 못 된다.** METR의 무작위 대조 실험에서 숙련 개발자는 AI로 20% 빨라졌다고 느꼈지만 실제로는 19% 느려졌다. 사람의 메모는 감지에는 쓸 수 있어도 "고쳤더니 나아졌다"의 근거로는 약하다.
2. **규칙을 쌓는 것은 공짜가 아니다.** 저장소 컨텍스트 파일(AGENTS.md 등)은 과제 성공률을 올리지 못했고 추론 비용을 20% 넘게 늘렸다. 불편할 때마다 규칙 한 줄을 더하는 방식은 그대로 두면 이 결과로 간다.
3. **하네스의 구성 요소는 낡는다.** Anthropic의 하네스 설계 글은 각 구성 요소를 "모델이 혼자 못하는 것에 대한 가정"으로 보고, 모델이 바뀌면 다시 확인해 걷어내라고 한다. 감지기와 그것이 낳은 규칙도 같다.
4. **원인이 프롬프트가 아닐 수 있다.** choco-pi는 Gemini 4 Neon의 `exec` 오류 15건 중 5건이 스키마의 `maxLength: 60` 제한 때문임을 찾아 코드에서 지웠다. 신호가 가리키는 곳을 읽기 전에 문구부터 고치면 틀린다.
5. **효과를 낸 요소는 예상과 다를 수 있다.** OMC 이슈 #1240은 비평 에이전트에 적대적 프레이밍을 붙여 지적 건수를 늘렸다고 보고했는데(n=7), 후속 분석에서 실제 요인은 적대적 프레이밍이 아니라 빠진 것을 열거하게 하는 구조화된 출력 템플릿으로 정리됐다. 귀속을 확인하지 않은 개선은 엉뚱한 것을 남긴다.
6. **넛지는 무시될 수 있다.** choco-pi 기록에는 모델이 `commit` 스킬을 읽고도 바로 다음 커밋 두 번을 규칙에 어긋나게 만든 세션이 있다.
7. **작은 개선은 성공률로 보이지 않는다.** 기존 문서의 교훈 1이다. 신호 발생 횟수는 성공률보다 분산이 작아서, 이 규모에서도 전후를 비교할 수 있는 후보다.

## 3. 제안: 메모에서 시작한다

지금 규모(사용자 한 명, 기록된 서브에이전트 실행 61회)에서는 자동 감지기보다 사람의 메모가 싸고 정확하다. 1절의 선례도 뼈대는 같다. Devin의 Knowledge Suggestions는 아래 1번을, Claude Code의 `/insights`는 2번을 자동화한 것이다.

1. **적는다.** 에이전트가 헛돌거나 사용자가 교정해야 했을 때 한 줄을 남긴다.
2. **모아 본다.** 주기적으로 메모와 `npm run signals` 출력을 함께 본다. `improver` 역할([.pi/agents/improver.md](../../.pi/agents/improver.md))에게 묶어 달라고 할 수 있다.
3. **하나만 고친다.** 두 번 이상 나온 것 중 하나를 골라, 원인이 있는 곳(프롬프트, 도구 설명, 코드)을 고친다. 모델이 읽는 텍스트를 바꿨으면 [model-guidance-history.md](../model-guidance-history.md)에 항목을 남긴다.
4. **다시 나오는지 본다.** 같은 메모가 또 쌓이면 효과가 없었던 것이다. 되돌리거나 다른 방법을 쓴다.
5. **걷어낸다.** 모델이나 Pi 버전이 바뀌면 이렇게 더한 규칙을 다시 확인하고, 더는 필요 없는 것을 지운다(근거 2, 3).

하지 않는 것:

- 세션 중에 모델이 읽는 텍스트를 스스로 고쳐 적용하지 않는다.
- 한 세션의 실패 하나로 규칙을 더하지 않는다. 재발한 것만 다룬다.
- "다시 안 나오더라"를 측정이라고 부르지 않는다. 이 절차의 4번은 체감이고, 근거 1이 그 한계다.

자동화는 같은 종류의 메모가 계속 쌓여 손으로 적기 번거로운 항목에만 붙인다. 그때는 무엇을 감지해야 하는지 이미 알고 있다.

## 4. 자동화로 넘어갈 때의 가설

자동 감지기를 만들기로 하면 아래를 의존 순서대로 확인한다. 앞 가설이 반증되면 뒤는 만들지 않는다. 임계치는 제안값이고, 데이터를 보기 전에 확정한다.

| | 가설 | 지표 | 반증 조건 |
|---|---|---|---|
| H0 존재 | 신호는 개선할 만큼 자주 생긴다 | 감지기별 세션당 발생률 | 5% 미만이면 그 감지기를 버린다 |
| H1 타당성 | 감지기가 잡은 것은 실제 문제다 | 적중 30–50건을 사람이 분류한 정밀도 | 70% 미만 |
| H2 예측력 | 신호가 있는 세션은 결과가 더 나쁘다 | 신호 유무별 사용자 교정률, 턴·토큰, 비정상 종료율 | 차이가 없다 |
| H3 귀속 | 반복되는 신호는 모델이 읽는 텍스트나 도구 설계에서 온다 | 신호가 특정 도구·역할·모델에 몰리는지, 원인 문구를 인용할 수 있는지 | 과제 종류에만 몰린다 |
| H4 개입 효과 | 귀속된 원인을 고치면 그 신호가 줄고 다른 지표는 나빠지지 않는다 | 수정 전후 발생률, 가드 지표(성공률, 토큰, 캐시 적중) | 변화가 무변경 구간의 변동폭 안이거나 가드 지표가 나빠진다 |
| H5 넛지 | 세션 중 넛지는 사후 수정에 더해 이득이 있다 | 넛지 on/off의 재발률과 토큰 | 재발률이 같거나 토큰만 는다 |
| H6 트리거 | 자동 알림은 수동 `npm run signals`보다 채택되는 개선을 더 낳는다 | 기간당 제안 수, 채택·기각 비율 | 알림만 늘고 채택은 그대로다 |

함께 적어 둘 대립 가설:

- 신호는 하네스가 아니라 모델과 과제 난이도가 결정한다. H3에서 갈린다.
- 신호를 줄여도 결과는 나아지지 않는다. 반복 호출을 억제했더니 탐색이 얕아지는 경우다. H4의 가드 지표가 잡는다.
- 넛지는 무시된다(근거 6). H5에서 갈린다.

규모:

- H0는 서브에이전트 쪽에서 일부 충족됐다. 기존 기록에서 reviewer 실행 32회 중 5회가 `finish` 없이 끝났다(약 16%). 최상위 세션은 기록이 없다.
- H4는 표본이 많이 든다. 발생률 16%를 5%로 낮춘 효과를 유의수준 5%, 검정력 80%로 잡으려면 조건당 약 120회, 8%로 낮춘 효과는 약 260회가 필요하다(두 비율 비교의 정규 근사). 그래서 실사용 기록으로는 큰 효과만 보고, 작은 효과는 신호를 유발하는 과제를 반복 재생해 잰다.
- H2는 상관이다. 어려운 과제일수록 신호도 많고 결과도 나쁘다. 인과는 H4에서만 확인된다.

### 후보 감지기

모두 결정적 규칙이다. 처음에는 기록만 하고 모델에게 알리지 않는다.

| 신호 | Pi 이벤트 | 비고 |
|---|---|---|
| 같은 도구를 같은 인자로 반복 호출 | `tool_call` | 폴링은 예외로 둬야 한다 |
| 같은 오류가 연속 | `tool_result` | |
| 사용자 교정(부정 응답, 턴 직후 중단) | `input` | 선례에서 가장 많이 쓰는 입력 |
| 편집 뒤 검사 없이 종료 | `agent_end` | |
| 도구 결과 하나로 컨텍스트 급증 | `turn_end` | |
| prefix 재작성, 낮은 캐시 적중 | `before_provider_request` | 서브에이전트에는 이미 있다 |
| 서브에이전트가 `finish` 없이 종료 | `classifyEnd` | 이미 있다 |

넛지를 붙이게 되면 도구 결과 끝에 붙인다. choco-pi가 쓰는 방식이고, 매 요청마다 위치가 바뀌는 리마인더가 캐시 표시를 가져가던 문제(PR #18)를 피한다. 넛지는 모델이 읽는 텍스트이므로 `prompt` 유형 PR의 근거를 따른다.

## 5. 지금 있는 것과 없는 것

- 있는 것: 종료 분류(`classifyEnd`의 `unanswered`, `drifted`, `budget_exceeded`, `idle`), 실행별 집계(`npm run signals`: finish 누락, 도구 오류, 계약 밖 호출, 반복, prefix 재작성, 캐시 적중), 편집 권한 없이 제안만 하는 `improver` 역할.
- 없는 것: 최상위 세션의 신호(지금은 서브에이전트 실행만 본다), 사람의 메모를 남기는 곳, 3일 넘는 보존(`requests.jsonl`은 3일 뒤 지워진다), 신호가 쌓였음을 알려 주는 트리거.
- 확인하지 않은 것: 표의 Pi 이벤트는 Pi 1.6.0 확장 문서에서 이름만 확인했다. 각 이벤트가 주는 값과 호출 순서는 구현 전에 읽어야 한다.
