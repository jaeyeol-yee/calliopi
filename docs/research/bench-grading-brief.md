# 브리프: 벤치마크 채점 강화

이 문서는 이 대화를 보지 못한 에이전트(Claude Code 클라우드 세션, Cursor Cloud Agent, 로컬 서브에이전트)가 혼자 이어서 일할 수 있도록 쓴 작업 지시입니다. 저장소를 처음 보는 사람이 읽는다고 가정합니다.

## 1. 배경

`bench/`는 Calliopi(Pi 하네스 확장 모음)의 모델 벤치마크입니다. 같은 과제를 실행 조건(모델 × effort × 하네스 버전)별로 반복해 돌리고, 결정적인 정답 검사(oracle)로 판정합니다. 결과는 세 곳에 쓰입니다.

- 모델별 경향과 버전 회귀를 `docs/model-guidance-history.md`에 근거로 남깁니다.
- 과제 종류별 임계점(목표 성공률에 닿는 가장 싼 모델 × effort)을 찾아 비용 최적화 하네스의 근거로 씁니다.
- 하네스 버전 사이의 차이(`harnessRef`)를 재서 프롬프트·역할 변경 PR의 Evidence로 씁니다.

먼저 읽을 것: `bench/README.md`, `bench/lib/task.ts`(과제 형식과 oracle), `bench/lib/report.ts`, `bench/tasks/*/*/task.yaml`, `bench/test/bench.test.ts`(과제마다 no-op은 실패, 기준 답은 통과), `docs/research/agent-self-improvement-evidence.md`(근거 기준).

## 2. 지금의 채점과 문제

지금은 과제마다 결정적 검사 몇 개를 두고 전부 통과하면 pass입니다.

| 검사 | 재는 것 |
|---|---|
| `command` | 제공된 테스트 통과 |
| `answer` | 최종 답 마지막 줄이 정규식과 맞음(정답 값, 줄 번호) |
| `file` contains/matches/absent | 파일 내용 |
| `unchanged` | 건드리면 안 되는 파일 |
| `scope` | 기록만 함(`outOfScope`), pass에 반영 안 됨 |

이것은 "목표 지점을 맞혔나"를 잴 뿐 "작업이 엄밀하게 유용했나"와 다릅니다. 실제로 관찰된 사례입니다(기록은 5절의 아카이브).

- **진단과 인용이 섞임.** `claude-sonnet-5-5`는 review 과제에서 버그 원인을 정확히 설명했지만 줄 번호를 하나 틀려(`review/spot-bug`에서 6 대신 5, `review/duration`에서 12 대신 11) fail이 되었습니다. S2에서는 effort high 이상에서 이 오류가 사라졌습니다.
- **과잉 보고가 그대로 실패.** `gpt-6.1-terra`는 `review/duration`의 두 버그를 찾고도 버그가 아닌 항목(큰 수 정밀도 등)을 덧붙여 fail이 되었고, effort가 높을수록 더 많이 덧붙였습니다.
- **잡지 못하는 것.** 줄 번호만 맞고 근거가 틀린 리뷰, 테스트 입력만 특수 처리한 수정, 범위 밖 수정은 지금 pass가 될 수 있습니다. diff가 최소인지, 불필요한 행동을 했는지도 재지 않습니다.
- **채점이 너무 좁았던 사례.** `review/pagination`은 처음에 8번 줄만 정답으로 받았지만, 9번 줄(같은 버그를 쓰는 slice)도 맞는 지적이라 v2에서 함께 받도록 고쳤습니다. 채점 규칙도 실제 모델 답으로 검증해야 합니다.

## 3. 이미 내린 결정 (바꾸지 않음)

1. **진단과 인용을 분리합니다.** review 과제는 "진단"(어떤 버그인지 맞게 짚었나)과 "인용"(줄 번호가 맞나)을 따로 통과/실패로 둡니다.
2. **추가 보고는 정밀도로 셉니다.** 진짜 버그를 모두 찾았으면 진단은 통과입니다. 버그가 아닌 추가 지적 수는 별도 지표(정밀도)로 기록합니다.
3. **범위 밖 수정은 실패입니다.** `scope`가 있는 과제에서 범위 밖 파일을 바꾸면 "범위" 차원이 실패합니다.
4. **점수는 여러 차원으로 냅니다.** 결과(정답·테스트), 진단, 인용, 정밀도, 범위, 숨긴 테스트를 각각 통과/실패(정밀도는 수치)로 기록합니다. "엄격 통과"는 해당 과제에 적용되는 모든 차원의 통과이고, 임계점 계산에는 엄격 통과를 씁니다. 가중 합산 점수는 만들지 않습니다.
5. **LLM 판정은 쓰지 않습니다.** 결정적 검사와 숨긴 테스트만 씁니다. LLM 판정은 사람 라벨로 보정할 수 있게 된 다음 단계에서 다룹니다.

## 4. 할 일

1. **차원별 채점으로 확장합니다.** `bench/lib/task.ts`의 oracle 형식에 차원을 붙이고(예: 검사마다 `dimension: outcome | diagnosis | citation | scope | hidden`), `runOracle`이 차원별 결과를 돌려주게 합니다. `RunRecord`와 `report.ts`는 차원별 통과율과 엄격 통과를 보여 줍니다. 기존 과제 형식(차원 없는 검사)은 `outcome`으로 읽혀야 합니다.
2. **진단 검사를 결정적으로 만듭니다.** review 과제의 진단은 답 전체에서 버그마다 근거 표현을 찾는 방식(예: `<=`·"at most once"·"lastIndex"처럼 버그별 키워드 묶음, 하나 이상 일치)으로 둡니다. 과제마다 기준 답과 실제 모델 답으로 오탐·미탐을 확인합니다. 정밀도는 답이 지목한 줄 중 버그 줄이 아닌 것의 수로 셉니다.
3. **숨긴 테스트를 추가합니다.** 수정 과제(small-fix, multi-file)마다 모델이 보지 못하는 테스트를 `bench/tasks/<class>/<name>/hidden/`에 두고, 실행 뒤 작업 디렉터리에 복사해 돌립니다. 제공된 테스트 입력만 특수 처리한 수정이 실패해야 합니다. 과제마다 "특수 처리 수정"을 하나 만들어, 제공 테스트는 통과하고 숨긴 테스트는 실패함을 `bench/test/bench.test.ts`에서 확인합니다.
4. **범위를 채점에 반영합니다.** `scope`가 있는 과제에서 `outOfScope`가 비어 있지 않으면 범위 차원을 실패로 둡니다.
5. **과제 버전을 올립니다.** 채점이 바뀐 과제는 `version`을 올립니다. 버전이 다른 결과는 섞이지 않습니다.
6. **기존 기록을 다시 채점합니다.** `bench/records/2026-11-27.tgz`(5절)를 풀어 새 채점으로 다시 매기는 스크립트(`bench/rescore.ts` 등)를 만듭니다. 모델을 호출하지 않습니다. 결과로 다음을 냅니다.
   - 스펙별 기존 판정과 새 판정의 비교표(차원별)
   - 판정이 바뀐 실행 목록(경로와 이유)
   - S1·S2 중간 결론(`docs/model-guidance-history.md`, PR #24 코멘트) 중 바뀌는 것
7. **문서를 고칩니다.** `bench/README.md`의 채점 설명을 새 방식으로 바꿉니다.

## 5. 기존 기록

`bench/records/2026-11-27.tgz`(약 1MB)에 2026-11-27의 실행 기록이 있습니다. 세션 파일과 서브에이전트 기록은 빠져 있습니다.

| 디렉터리 | 내용 |
|---|---|
| `s1-coarse` | 모델 6개 + 대조군, medium, 과제 8개 × 3회 (216회). 하네스는 #23 이전 |
| `s2-effort` | terra·sol·sonnet·opus의 effort 훑기, 1회차 과제 9개 (188회, 중단) |
| `pr-delegation` | #23 전후 비교, 과제 6개 × 2회 (96회) |
| `s0-calib`, `s0-hard` | 어려운 과제 난이도 확인 (36회) |

각 디렉터리의 `runs.jsonl`이 실행별 기록(`RunRecord`: 모델, effort, 과제와 버전, 검사 결과, 바뀐 파일, 비용, 최종 답의 마지막 2000자)이고, `runs/<arm>/<task>/rep<N>/`에 `answer.txt`(전체 답), `stderr.txt`, `work/`(실행 뒤 남은 파일)가 있습니다. 다시 채점할 때는 `work/`와 `answer.txt`를 씁니다. 과제 fixture는 `bench/tasks/`에 있으므로 실행 전 상태는 fixture에서 얻습니다.

## 6. 제약

- 모델을 호출하지 않습니다(`npm run bench`로 실제 모델 spec을 돌리지 않음). 필요하면 faux smoke(`bench/specs/smoke.yaml`)만 씁니다. 실제 모델 실행이 꼭 필요하다고 판단되면 하지 말고 이유와 예상 비용을 보고합니다.
- 채점 기준을 기존 결과가 좋아 보이도록 맞추지 않습니다. 판정이 바뀐 사례는 모두 목록으로 남기고, 사람이 그중 일부를 확인할 수 있게 경로를 적습니다.
- 브랜치를 새로 만들고 PR로 올립니다. 커밋 메시지는 영어, PR 본문은 `.github/PULL_REQUEST_TEMPLATE/tool.md` 형식(영어)을 따릅니다.
- 커밋 trailer: `Co-authored-by: Claude Code <noreply@anthropic.com>`, `Assisted-By: Claude Code(<모델>)`.
- 작업 디렉터리 밖에 쓰지 않습니다(임시 파일은 OS 임시 디렉터리).

## 7. 완료 조건

- 과제 12개 모두에 차원별 채점표가 있고(`task.yaml`), 수정 과제마다 숨긴 테스트와 그것을 검증하는 "특수 처리 수정" 테스트가 있습니다.
- `npm run bench:test`, `npm run typecheck`, `npm run check:imports`가 통과합니다.
- 재채점 스크립트가 아카이브의 기록을 모두 다시 매기고, 6항의 비교표와 바뀐 실행 목록을 PR 본문(또는 `bench/records/rescore-2026-11-27.md`)에 남깁니다.
- 열린 질문(아래)에 대한 제안이 PR에 있습니다.

## 8. 열린 질문 (제안만 하고 결정은 사람이)

- 진단 키워드 묶음이 다른 표현의 맞는 답을 놓치는 비율을 어떻게 관리할지(과제별 허용 표현 목록, 사람 라벨 몇 건으로 점검 등).
- 숨긴 테스트가 과제의 의도보다 엄격해지는 경우(과제 설명에 없는 동작을 요구)를 어떻게 막을지.
- 과정 지표(diff 크기, 불필요한 도구 호출)를 채점 차원에 넣을지, 경향 지표로만 둘지.
